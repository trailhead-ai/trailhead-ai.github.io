trailhead

AI can write the code. You’re still the engineer.

On its own, a coding agent starts every session from scratch, in a single repo, with no memory of what you already decided. Trailhead changes that - durable memory, a workspace that spans every related repo, and a process it actually follows - so working with it feels less like directing a tool and more like building alongside another engineer.

Why it exists

Built because one engineer had to ship a whole product.

Trailhead did not start as a thesis about AI tooling. It started as the daily kit of a sole engineer carrying an entire product: a backend, a web app, an iOS app, the infrastructure underneath, and the AI on top of it. The agents were good at writing code and bad at everything around it. They forgot yesterday’s decisions. They had nowhere to work. They one-shot a hack when the job needed a plan.

So the gaps got filled, one painful Tuesday at a time. What ties the tools together is not a clever theory about AI; it is a plain goal - let the agent work the way a good engineer already works. Carry what it learned in one session into the next. Work across the several repos a real product spans, not one at a time. Keep track of the decisions, the lessons, and the dead-ends, so the next change builds on them instead of rediscovering them. The closer the agent works to how you work, the less time you spend re-explaining yourself and the more it feels like building alongside someone instead of managing a tool.

What is left is a small, sharp toolset that maps to what a coding agent is missing on its own - memory, environment, process, and the long tail of actually shipping. They share one organizing idea: the unit of work is not a repo, it is a group of related repos. Memory is shared across the group, a workspace spans the group, and a release ships the group as one. That is the part most AI tooling skips, and it is where real products actually live.

The suite

Built for what a model lacks.

lore

Memory

Agents forget everything between sessions. lore is durable, structured project memory - a git-backed, plain-text vault of decisions, dead-ends, deferred work, and session notes. The things most tools never write down (what you tried and abandoned, what you are waiting on) are first-class here, and a session note carries the thread from one sitting to the next - so you start warm instead of re-explaining the project every morning.

Memory comes in layers - a personal layer that follows you across everything you build, and a shared layer scoped to the group. So a dead-end you hit in one project is there to warn you in the next, and a decision the group made lives above the repos instead of being trapped in one. No service to run and no MCP server: the agent reads and writes through the lore CLI and git, and pulls back the slice that bears on what you are doing.

camp

Environment

Real products are rarely one repo. camp treats a group of related repos as a single unit: one workspace cuts a git worktree across every repo in the group on a matching branch, provisioned by per-repo setup tasks so the whole thing comes up from a single command.

The unit of work becomes the whole product, not a lone checkout. Workspaces are isolated from each other, so you can keep several changes going at once without them colliding - and a bookmark points from a workspace back to the agent session you were running in it, so you can walk away and pick it up later.

craft

Process

One-shot prompting does not do real engineering. craft is a roster of specialized subagents and a test-driven workflow that runs the real arc of a change - shape it, attack the spec before it freezes, plan it, prove the risky assumptions, build it test-first, then review - and treats that plan as a starting point, not a contract. It expects you to learn as you go: the agent proves shaky assumptions before anything gets built on them, and holds each decision until you actually have the facts to make it.

The work is split across isolated subagents rather than piled into one context - a TDD implementer per slice, a conformance gate behind it, a four-lens council when a decision is genuinely hard. Process, encoded - so the agent works the way a careful engineer would, not something that looks finished until you look closer.

portage

Shipping

Shipping a change across several repos opens a window where one repo is ahead of the others. portage closes it - it treats the linked pull requests for a change as one release, watches CI on each, triages the failures and the review comments as they come in, and merges in the dependency order you declared so the group moves together instead of drifting out of sync.

The unit of release becomes the group, not a lone pull request. Merging is opt-in and fail-closed: without explicit authorization in the group config, portage refuses to merge anything at all.

outpost

Review loop

Reviewing an agent’s work by scrolling a terminal is the wrong shape for the job. outpost turns it around: you read the diffs, specs, and decision records in a local web cockpit and leave inline comments, then the agent picks those comments up, acts on each one, and replies - applying the change or pushing back with a reason.

It binds to loopback only, and the actions that must be human - authoring a review, resolving a comment - are gated behind a browser session the agent never holds. Your review text is treated as data to act on, never as instructions to obey. Requires a companion cockpit application that is not yet publicly released - see the docs before you plan around it.

Coordinated multi-repo work

Three questions single-repo tooling can’t answer.

1

Where does cross-repo knowledge live?

A decision made in the backend constrains the client, and the knowledge that matters most is exactly the knowledge that spans repos. lore keeps memory above the repos, scoped to the group rather than trapped in one - so a call made while working in one repo is there in any sibling it touches.

2

How does one change span several repos?

A single feature is often a backend change and a client change and an infra change at once. camp cuts one workspace across every repo in the group on matching branches, so the unit of work is the whole change - built and tested together before any of it lands.

3

How do they ship without breaking each other?

Split a change across repos and you open a window where one is ahead of the others. portage lands the pieces as linked pull requests treated as one release - merged in the dependency order you declare - so that window never opens.

Token economy

Built to spend fewer tokens, not more.

Most agent tooling quietly inflates your context - more rules, more files, more transcript dragged along every turn - and you pay for it on every call. Trailhead treats the opposite as a design goal: where a choice can do the same job for fewer tokens, it takes it. A few of the ways that shows up:

Specialized subagents on the right model. craft hands the bulky, low-judgment work - reading test logs, diffs, CI output, long files, wide searches - to small subagents running on the cheapest capable model. Only their conclusion comes back, so the expensive model never pays to read the raw stream.

Recall that loads only what is relevant. lore pulls the slice of memory that bears on what you are doing, not the whole vault - so recall cost scales with relevance, not with how much you have piled up. And because every note is typed and conventional in shape, the agent spends little effort working out what a document is and whether it matters.

Checkpoint, then clear. lore can snapshot the state that matters from a session into its notes - so when a context window fills with noise you can compact or clear it and pick the thread back up warm, instead of dragging a bloated transcript along just to keep your place.

Install only what you will use. Every skill and agent you wire in costs context on every turn. Trailhead lets you pick capabilities - down to the individual subagent or skill - so you never pay context for power you are not using.

Get started

Clone it and run one command.

There is no package to download and no pip install step - the checkout is the source. The installer auto-detects your harness, wires in the plugins you asked for, and puts the plugin CLIs on your PATH.

$ git clone https://github.com/trailhead-ai/trailhead.git
$ cd trailhead
$ ./bin/trailhead install
# then add the shell line it prints to your profile, and restart your shell
$ eval "$(/path/to/trailhead/bin/trailhead shellenv)"
Requires Python 3.11 or newer and no third-party packages. After installing, restart your shell so the CLIs resolve and start a fresh agent session so the plugins load. Full walkthrough in the installation guide, or jump to the quickstart to set up your first group.

The shape of it

It works with you, not for you.

Trailhead does not force a way of working on you. The tools are separate on purpose - take lore for memory and keep whatever workflow you already like, whether that is a framework like superpowers or plain old Plan mode. craft’s process is there when you want structure and out of the way when you don’t. You wire up the parts that help and leave the rest.

Left alone, a model will happily act on a guess and hand you something confident and wrong. Trailhead does not make the model smarter - it gives your agent the habits of a careful engineer: prove a shaky assumption with a throwaway test before building on it, go research what it does not know instead of inventing it, and review its own work against the plan before calling it done. The model still does the thinking; Trailhead just makes sure it shows its work.

Questions

The short answers.

Do I have to use all of them? +

No. Install as many or as few as you like - down to the individual subagent or skill. lore is a memory layer for any agentic setup, camp is multi-repo worktree orchestration, craft is the planning and execution workflow. Adopt one, some, or all of them. craft is never a dependency of the others.

Most people start with lore and grow into camp and craft as the need shows up.

Does this replace my note-taking app? +

No. lore is agent-native project memory - typed, machine-readable knowledge the agent captures and recalls to do work. It does a different job than a personal knowledge base, and it sits happily alongside whatever you already use for notes.

Does my code or data leave my machine? +

No. Everything is local-first and plain-text - a git-backed vault and plain files on disk. There is no cloud service in the loop and nothing phones home, which also makes the suite a fit for regulated environments. There is no MCP server to run either: the agent works through the CLIs over your shell.

Which agent harness does it work with? +

Trailhead is harness-neutral by design - every capability wires through a harness seam, a single interface between the tools and whatever agent is driving them. Claude Code is the harness that ships today. Supporting a new one means implementing that one interface and registering it; it requires no changes to the shared install path.

Does it work with GitLab, or another host? +

Not yet. lore, camp, and craft are host-agnostic - they only need git. portage reaches a code host to open, watch, and merge pull requests, and GitHub is the only provider implemented today. The provider sits behind its own interface, so adding another is a contained change rather than a rewrite.

Can my team or company self-host it? +

Yes. Forked and self-hosted installs are first-class - point it at your own repositories, run the whole suite off your own infrastructure, no hardcoded upstream and no callbacks required. Installing from your own fork is the same clone-and-run flow.

How do I upgrade? +

git pull in the checkout and re-run ./bin/trailhead install. Upgrades are additive - re-running install only adds, so removing something from your config never removes it from the install. To drop pieces, uninstall and re-install with a narrower config. Uninstalling keeps your data: the vault, your groups, and each plugin’s data survive a later re-install.

What does it cost? +

Nothing. Trailhead is open source under Apache-2.0 - free to use, free to fork. You pay your model provider for tokens, as you already do.
