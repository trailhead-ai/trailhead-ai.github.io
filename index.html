trailhead

AI can write the code. You’re still the engineer.

On its own, a coding agent starts every session from scratch, in a single repo, with no memory of what you already decided. Trailhead changes that - durable memory, a workspace that spans every related repo, and a process it actually follows - so working with it feels less like directing a tool and more like building alongside another engineer.

Why it exists

Built because one engineer had to ship a whole product.

Trailhead did not start as a thesis about AI tooling. It started as the daily kit of a sole engineer carrying an entire product: a backend, a web app, an iOS app, the infrastructure underneath, and the AI on top of it. The agents were good at writing code and bad at everything around it. They forgot yesterday’s decisions. They had nowhere to work. They one-shot a hack when the job needed a plan.

So the gaps got filled, one painful Tuesday at a time. What ties the tools together is not a clever theory about AI; it is a plain goal - let the agent work the way a good engineer already works. Carry what it learned in one session into the next. Work across the several repos a real product spans, not one at a time. Keep track of the decisions, the lessons, and the dead-ends, so the next change builds on them instead of rediscovering them. The closer the agent works to how you work, the less time you spend re-explaining yourself and the more it feels like building alongside someone instead of managing a tool.

What is left is three small, sharp tools that map to the three things a coding agent is missing on its own - memory, environment, and process. They share one organizing idea: the unit of work is not a repo, it is a group of related repos. Memory is shared across the group, a workspace spans the group, and a release ships the group as one. That is the part most AI tooling skips, and it is where real products actually live.

The suite

Three tools for the three things a model lacks.

lore

Memory

Agents forget everything between sessions. lore is durable, structured project memory - a git-backed, plain-text vault of decisions, dead-ends, deferred work, and session notes. The things most tools never write down (what you tried and abandoned, what you are waiting on) are first-class here, and a session note carries the thread from one sitting to the next - so you start warm instead of re-explaining the project every morning.

Memory comes in layers - a personal layer that follows you across everything you build, and a shared layer scoped to the group. So a dead-end you hit in one project is there to warn you in the next, and a decision the group made lives above the repos instead of being trapped in one. Either way the knowledge compounds instead of resetting to zero.

camp

Environment

Real products are rarely one repo. camp treats a group of related repos as a single unit: one worktree spans every repo in the group on matching branches, with everything the product runs on stood up together in one dev environment from a single command.

The unit of work becomes the whole product, not a lone checkout. And because camp can bring each worktree’s dev environment up in parallel, isolated from the rest, you can keep several going at once without them colliding.

forge

Orchestration

One-shot prompting does not do real engineering. forge is a roster of specialized subagents and a test-driven workflow that runs the real arc of a change - design it, plan it, prove the risky assumptions, build it test-first, then review - and treats that plan as a starting point, not a contract. It expects you to learn as you go: the agent drafts a mockup you can react to before any code is written, proves the shaky assumptions before anything gets built on them, and holds each decision until you actually have the facts to make it. The plan adapts as the work does.

Process, encoded - so the agent works the way a careful engineer would, not something that looks finished until you look closer.

Coordinated multi-repo work

Three questions single-repo tooling can’t answer.

1

Where does cross-repo knowledge live?

A decision made in the backend constrains the client, and the knowledge that matters most is exactly the knowledge that spans repos. lore keeps memory above the repos, scoped to the group rather than trapped in one - so a call made while working in one repo is there in any sibling it touches.

2

How does one change span several repos?

A single feature is often a backend change and a client change and an infra change at once. camp cuts one worktree across every repo in the group on matching branches, bound by a manifest, so the unit of work is the whole change - built and tested together in one dev environment before any of it lands.

3

How do they ship without breaking each other?

Split a change across repos and you open a window where one is ahead of the others. forge lands the pieces as linked pull requests treated as one release - merged in dependency order, and the preview soaked together as a unit - so that window never opens.

Getting started

Install the manager, then wire what you need.

Trailhead ships as a small management CLI plus the three plugins. Each tool is self-contained and independently adoptable - wire all three, or just the one you want.

$ git clone https://github.com/trailhead-ai/trailhead.git
$ cd trailhead
$ pip install .

$ trailhead install                  # wire all three plugins
$ trailhead install --preset minimal # wire lore only
Heads up: installing the package only gives you the trailhead manager. Run trailhead install to actually wire the tools into your agent harness - nothing is active until you do.

The shape of it

It works with you, not for you.

Trailhead does not force a way of working on you. The tools are separate on purpose - take lore for memory and keep whatever workflow you already like, whether that is a framework like superpowers or plain old Plan mode. forge’s process is there when you want structure and out of the way when you don’t. You wire up the parts that help and leave the rest.

Left alone, a model will happily act on a guess and hand you something confident and wrong. Trailhead does not make the model smarter - it gives your agent the habits of a careful engineer: prove a shaky assumption with a throwaway test before building on it, go research what it does not know instead of inventing it, and review its own work against the plan before calling it done. The model still does the thinking; Trailhead just makes sure it shows its work.

Questions

The short answers.

Do I have to use all three tools? +

No. Each one stands on its own - lore is a memory layer for any agentic setup, camp is multi-repo worktree and dev-environment orchestration, forge is the planning and execution workflow. Adopt one, two, or all three. forge is never a dependency of the other two.

Does this replace my note-taking app? +

No. lore is agent-native project memory - typed, machine-readable knowledge the agent captures and recalls to do work. It does a different job than a personal knowledge base, and it sits happily alongside whatever you already use for notes.

Does my code or data leave my machine? +

No. Everything is local-first and plain-text - a git-backed vault and plain files on disk. There is no cloud service in the loop and nothing phones home, which also makes the suite a fit for regulated environments.

Which agent harness does it work with? +

Trailhead is built harness-neutral. The real work lives in plain CLIs and a plain-text vault behind a thin adapter, so it wires into your agent rather than locking you into one.

Can my team or company self-host it? +

Yes. Forked and self-hosted installs are first-class - point it at your own repositories, run the whole suite off your own infrastructure, no hardcoded upstream and no callbacks required.

What does it cost? +

lore, camp, and forge are open source under Apache-2.0. Free to use, free to fork.
