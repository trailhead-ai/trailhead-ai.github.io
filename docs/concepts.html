Getting started

Concepts

Trailhead's plugins share a small vocabulary. Learning these terms once makes every plugin page read easily, and makes it obvious why the tools fit together the way they do.

The group

A group is a named set of repositories that are worked on together — a backend, a web client, a mobile app, and the infrastructure that runs them. It is the single organizing idea underneath the whole suite:

  • Memory is scoped to the group, so a decision made in one repository is available in every sibling it touches.
  • A workspace spans the group, so one change can cut across every repository at once.
  • A release ships the group, so the pull requests for a change merge together rather than drifting apart.

Each repository belongs to exactly one group — overlap is not allowed, and the rule is enforced rather than merely advised. A member is one repository's entry in the group, carrying its path and its provisioning steps. If you work in a single repository, a group of one is perfectly reasonable; the design simply assumes most real products are not.

Group definitions live in ~/.config/camp/groups/<name>.toml and are plain, hand-editable TOML. They are the one piece of configuration worth understanding properly, because both camp and portage read from them.

Workspaces and worktrees

A workspace is one unit of work across the whole group. Creating one cuts a git worktree in every member repository, all on a matching branch, then runs each member's provisioning steps so the thing is ready to work in.

A workspace is addressed by its slug — a short name you choose, like add-billing. The slug feeds the branch pattern configured for the group (commonly something like worktree-{slug}), which is how every member ends up on a consistently named branch.

Because worktrees are separate directories, workspaces are isolated from one another. You can have several changes open at once without them colliding, and tearing one down does not disturb the others. Drift is the term for a workspace whose branches have fallen behind their upstreams.

The vault and its records

A vault is a git repository full of markdown files — this is where memory lives. Each file is a record: a typed, structured note with frontmatter that the agent can search, filter, and link.

There is a closed set of nine record kinds. The set is deliberately fixed; a small taxonomy the agent knows completely is worth more than an open-ended one it has to interpret.

KindWhat it records
decisionA choice that was made, and why — the lightweight, in-flight capture
adrAn architecture decision record: a considered, durable design decision
lessonSomething learned the hard way, including dead-ends worth not repeating
taskA unit of work — open, ready, blocked, or done
areaA profile of one area of the codebase: what it is, how it behaves, its gotchas
specWhat a change is meant to achieve, before it is planned
collaborationWorking agreements and context about the people involved
blobUnstructured material that does not fit another kind
sessionThe running log of one working session

Each kind carries its own status vocabulary — a task moves through open, ready, blocked, and done, while an ADR moves through draft, active, and superseded. Records link to each other with [[wikilinks]].

Layered vaults

You have more than one vault, and they are searched together. A personal default vault follows you across everything you build; additional vaults are scoped, so knowledge that belongs to a product or a team lives above any single repository. Records route to a vault by scope — repo, product, suite, or team — and anything without a matching scope binding lands in default.

The practical effect: a dead-end you hit on a personal project is there to warn you at work, while a decision your team made stays in the team's vault rather than being trapped in one checkout.

Areas and the area map

An area profile is the agent's mental model of one part of the codebase. The area map is the compact list of those profiles, which the agent scans to decide what is worth pulling into context. It is the mechanism that keeps recall proportional: the agent reads a short menu, not the whole vault.

Sessions, candidates, and the flush

While working, the agent captures findings as candidates on the current session record — cheap, liberal, judgment-deferred. Capturing is meant to be almost free, so nothing is lost to hesitation.

At the end (or any time you like), a flush reviews the outstanding candidates, promotes the ones that deserve to last into durable records, and marks the session clean. A watermark tracks what has already been flushed, so a second flush only considers what is new.

Recall is pull-based: the agent searches the vault when it decides it needs to. Nothing automatically injects memory into your conversation.

Specs, plans, slices, and tasks

This vocabulary belongs to craft, which runs the arc of a change.

  • A spec states the problem, the objectives, the acceptance criteria, and the non-goals. It starts as a draft and freezes once it has survived review — after that, new thinking means a new spec rather than a quiet edit.
  • The gauntlet is that review: parallel adversarial passes that attack a draft spec from independent angles before it freezes.
  • The council is a panel of four lenses — builder, breaker, attacker, advocate — convened on a hard decision and then synthesized.
  • A plan turns a frozen spec into ordered slices. Each slice is independently committable and gets built and checked on its own.
  • A standalone task is a leaf with no parent plan and no child slices — a single self-contained piece of work. Refining one promotes it from open to ready by filling in what it delivers, how it will be tested, and which files it touches.
  • An ADR records a design decision durably. Once active it is treated as immutable — changing your mind means writing a new ADR that supersedes it.

Harnesses, plugins, skills, and subagents

A harness is the agent application you drive — Claude Code today. Trailhead never speaks to a harness directly from its shared code; everything goes through the harness seam, one interface that harness-specific code implements. Adding a new harness means writing that one implementation, with no changes to the shared install path.

A plugin is one of the five tools. What a plugin actually gives your agent comes in two forms:

  • A skill is a procedure the agent follows — invoked by name, like /craft:plan, or triggered when the situation matches.
  • A subagent is a specialist dispatched into its own fresh context to do one job and report back a conclusion. This is what keeps bulky work — reading logs, diffs, wide searches — from filling up the main conversation.

You can install plugins individually, and within a plugin you can install individual skills and subagents. Everything you wire in costs context on every turn, so narrow installs are a genuine optimization.

How the plugins reference each other

The plugins are separable, but they do know about each other in specific, documented ways:

DependencyWhy
craft → lorecraft stores specs, plans, tasks, and ADRs through a note store; lore is the only implemented provider
portage → campportage reads the repository set and release settings from the camp group definition

craft is never a dependency of the others, and lore and camp stand alone. The arrows only ever point toward the simpler tools.

Paths

Trailhead follows the freedesktop base directory specification on every platform, macOS included — configuration under ~/.config, state under ~/.local/state, cache under ~/.cache, with the XDG_* variables taking precedence when set. This is a deliberate departure from the macOS-native ~/Library/Application Support layout, chosen so one mental model covers every machine you work on.
