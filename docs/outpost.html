Plugins

outpost — cockpit

A local daemon and web UI that watches your lore vaults, flags the ones that need you, and serves every vault record and published site as a browsable reader — plus two skills that let the agent hand you pages and sketches to look at instead of walls of text.

The outpost daemon has not been publicly released. Read the cockpit sections of this page as a description of what is coming, not as something you can run.

trailhead ships the agent side; the daemon lives elsewhere. trailhead install installs the outpost plugin (two skills, a session hook, and an always-loaded rule) and the trailhead outpost lifecycle verbs. The web application those verbs manage is a separate checkout that is not part of the trailhead repository; its repository is not public, so only accounts that have been given access can clone and build it.

The lifecycle verbs need that checkout. trailhead outpost reads ~/.config/outpost/config.toml and requires a checkout key holding the absolute path of a built outpost checkout. Without one, trailhead outpost start has nothing to start and fails cleanly saying so.

Some of the skills work without it. A scratch pad opened outside a camp workspace is plain files with a file:// link, and opens with nothing running. /publish-site into a vault validates, writes, and syncs with no daemon at all — but the link it prints is served by outpost, so you need the daemon to view what you published. Anything published into a camp workspace is only viewable through outpost.

What it is for

Run several agent workstreams at once and the hard part stops being the work and becomes knowing which stream needs you. A terminal tells you about the one you are looking at. Your vaults keep filling with specs, decisions, and tasks you only see if you go looking.

outpost is the one place you look. It runs on your machine, reads the same camp group files camp reads to find the lore vaults your groups use, and keeps a live view of them in a browser tab. When a vault stops syncing it says so, and it is also where every link the agent prints for a record or a page actually opens.

outpost is a lens, not a control panel. It displays state and leaves changes to the tools that own them: you remove or rebase a workspace with camp, and you edit records with lore.

What the cockpit shows

SurfaceWhat you get
HomeFull-text search across every configured vault — the front door, and where any unknown address lands
VaultRecords browsed by kind and by vault — specs, ADRs, tasks — with the lineage between them drawn as a tree
EffortsEvery design record grouped under the decision record it belongs to, so you can see which pieces of work hang together
SitesEvery static site published into a vault, each a link to the page itself
Record pagesOne page per record, at a stable address: /records/<vault>/<kind>/<slug>

Records at stable addresses

The record address is a contract shared with lore: when the lore CLI writes a record it prints a link in that form, pointing at http://127.0.0.1:7313 unless you configure another base. Click it in your terminal and the record opens in outpost. Reading a record needs no login, so a printed link resolves straight away. If the daemon is stopped, the link has nothing to open and nothing else breaks.

Vaults that need you

Each vault carries a sync state — up to date, holding changes, needs a person, or can’t sync — with a one-line reason and, where there is one, the command that fixes it. You can start a sync from the interface. When a vault stays stuck past a threshold (30 minutes by default), outpost raises a browser notification, so a vault that quietly stopped syncing does not stay invisible.

Pages to look at, not text to scroll

outpost serves static sites on a second loopback listener (port 7314 by default), separate from the cockpit. A site is any directory with an index.html at its root; extra pages, CSS, and images are expected. Sites come from two places, and the choice between them is about how long the page should live:

  • A lore vault’s sites/ tree — shared with the team. Publishing is a vault commit plus a sync; there is no build step and no hosting service. Every teammate running their own outpost opens it at http://127.0.0.1:7314/<vault>/<slug>/.
  • A camp workspace’s sites/ tree — scoped to one piece of work. It syncs nowhere, is never shared with teammates, and disappears when the workspace is torn down. That lifetime is the point: a PR walkthrough or a one-off analysis should not outlive the work it was for.

Serving is deliberately simple: directory index pages, a redirect to the trailing-slash form, content type by file extension, and a 404 for everything else. Symlinks, non-regular files, and path traversal are refused. Every page is served with a content policy that blocks requests to any origin other than the page’s own, and the sites listener never sees the cockpit’s login cookie, so a published page cannot act as you in the cockpit. If the sites port is already taken, the cockpit keeps running without sites.

The plugin

The outpost plugin is what the agent sees. It has no command-line tool of its own and no subagents; the daemon verbs live in the trailhead CLI.

PieceWhat it does
/publish-sitePublishes a multi-file static site into a vault’s sites/ tree, or into the current camp workspace’s, and hands back the link
/scratch-padDraws a design question’s options as hand-drawn sketches — screen layouts or process flows — so you compare drawings instead of reading descriptions
Always-loaded ruleTells the agent to publish an HTML deliverable you are meant to look at — a report, dashboard, design doc, runbook — as a site instead of leaving a stray file, how to pick vault or workspace, and when to reach for a scratch pad
Session hookRegisters the agent session with outpost whenever a session starts, resumes, clears, or compacts. It never blocks or fails the session; when registration does not succeed, the reason is recorded as one line in a log

publish-site

The skill takes a source directory and a slug matching ^[a-z0-9][a-z0-9._-]*$, and the agent picks exactly one target: a vault or a workspace. The bundled script validates before writing anything — symlinks and other non-regular files are rejected, and no path segment may contain .., a backslash, or a NUL byte — then publishes atomically, so the served directory is always either the whole old site or the whole new one.

Republishing an existing slug requires --overwrite; without it you get a file-level add: / change: / remove: preview and no write. For a vault, the script runs the vault sync itself and prints the link only when that sync succeeded, so a publish that never reached your teammates is never reported as live. A workspace link is printed with a line saying who can open it and that it dies with the workspace, so it can never be mistaken for a shared one. Removing a site is deleting its directory, followed by a sync for a vault.

scratch-pad

When a design question’s options differ in how something looks or how a process runs, the agent writes the options as a short JSON description — a layout tree or a flowchart per option, a line on what each costs, and its own recommendation marked — and the bundled script draws them as a pad of pages in your browser. Follow-up questions on the same design are added to the same pad as a new round; earlier rounds stay reachable.

A pad is scratch and is never published to a vault. Inside a camp workspace it becomes a site of that workspace, opened through outpost. Outside one it is plain files on disk with a file:// link that needs nothing running. When you name a drawing as the one to build or keep, the agent can publish just that drawing to a vault as a reference page the team can open.

Daemon management

The trailhead CLI owns the daemon’s lifecycle. The daemon binds 127.0.0.1 only, and the cockpit is at http://127.0.0.1:7313/.

CommandBehavior
trailhead outpost startValidates the configured entrypoint, then starts the daemon detached so it survives the CLI exiting. Idempotent: a second start while it is answering is a no-op
trailhead outpost stopStops the daemon and waits for it to exit. A no-op when nothing is running
trailhead outpost statusReports liveness plus a health probe, with structured exit codes (below)
trailhead outpost restartRebuilds the checkout first, then restarts. A broken build leaves the running daemon untouched. Also works as “build and start” when nothing is running
trailhead outpost openOpens the cockpit in your browser — only once the daemon is answering; otherwise it tells you to start it
trailhead outpost enableRegisters the daemon with your host’s supervisor — launchd on macOS, systemd --user on Linux — so it starts at boot or login and is restarted after a crash
trailhead outpost disableDeregisters and removes that supervisor entry. A no-op when nothing is registered

Once a supervisor entry is registered, start, stop, restart, and status drive the supervisor instead of running the daemon themselves. A crash brings the daemon back; your own stop leaves it stopped. enable checks before writing anything: the build must exist and node, git, lore, and tmux must all be on your PATH. On Linux it also turns on lingering (loginctl enable-linger) so the daemon can start with nobody logged in, and prints the exact command to run by hand if it cannot.

Status exit codes

Exit codeMeaning
0Running, confirmed by the health probe
3Stopped
4Stale: a leftover record pointed at a dead process, and has been cleaned up (without a supervisor)
5Restarting: the supervisor has a process, but it is not answering yet (with a supervisor)
6Failed: the supervisor gave up on the job; the recovery command is printed (with a supervisor)

A recorded process ID is never trusted on its own: operating systems reuse them, so every verb confirms the process actually answers the health probe before signalling it. A dead daemon shows in the browser as a plain connection failure; run trailhead outpost status, then start, then reload.

The security model

The agent and you read the same cockpit, and the agent must not be able to act as you inside it.

  • Loopback only. Both listeners bind 127.0.0.1. outpost is a single-operator tool on a single machine; teammates each run their own.
  • Reads are open; changes need you. Reading needs no credential, which is why a printed record link just works. Every request that changes anything needs a session cookie that the daemon gives only to your browser. It is never written anywhere the agent can read, never returned in a response, and never logged — so the agent has no way to send it. Changes are also checked against an origin allowlist, so another website cannot drive them from your browser.
  • A separate operator tier. A small set of operator routes accepts only a per-boot credential, written at startup to a private file that only you can read; every restart mints a new one. It grants nothing on the cookie-protected routes, and the browser cookie grants nothing on it.

Honest limits

The daemon is not publicly released. This is the big one. The lifecycle verbs manage a daemon you cannot currently obtain, and every link the skills and lore print points at it.

Single operator by design. outpost binds loopback and has no multi-user story. Sharing happens through the vault: a teammate sees a published site because they sync the vault and run their own outpost, not because they reach yours.

It observes; it does not change your work. outpost will not remove, rebase, or open a workspace, or edit a record. Those stay with camp and lore. The one thing it starts is a tmux hub session, and only on an authenticated operator request.

Claude Code is the only harness implemented. As with the rest of the suite.
