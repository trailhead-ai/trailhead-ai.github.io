Getting started

Quickstart

This walks through your first hour: confirming the install, capturing your first memory, defining a group, opening a workspace, and running a change through to a pull request. Adopt as much or as little of it as you like — the first two steps are worth doing on their own.

Before you start, work through the installation guide, add the shellenv line to your shell profile, restart your shell, and start a fresh agent session.

Step 1 — Confirm the install

Two checks. First, that the plugins and CLIs are wired up:

$ trailhead doctor

You want to see your harness listed with the plugins you installed, and each CLI resolving to a path inside the shim directory. Then confirm the memory vault exists and is healthy:

$ lore status
$ lore vault ls

The installer creates a default vault as a git repository. If lore vault ls shows it, memory is ready to use.

Step 2 — Capture your first memory

This is the highest-value thing to adopt first, and it works no matter what else you install.

Memory is meant to be captured by the agent as you work, not typed up by you afterwards. In a session, when you settle something worth keeping — a decision, a gotcha, a dead-end — tell the agent to record it:

# in your agent session
Record that we chose cursor-based pagination over offset because
the offset query degrades past about 50k rows.

The agent captures that against the current session as a candidate. Candidates are cheap and liberal by design — the judgment about what deserves to last happens later. At the end of the session, or whenever you like, promote them:

# in your agent session
/lore:flush

That reviews the outstanding candidates, writes the ones worth keeping as durable records, and marks the session clean. Now search them back:

$ lore search 'pagination'
$ lore search 'kind:decision'
$ lore search 'kind:lesson and pagination'

The query language is a small subset of KQL: bare words do full-text search, field:value filters, and you can combine terms with and, or, and not. Add --limit to widen the default of 20 results.

Write to the vault through the CLI, never by editing files. The installer wires in a guardrail that blocks direct edits to vault files, because hand-edited records break the index and the record contract. This is deliberate, not an obstacle to route around.

That is the whole loop: capture liberally while working, flush at the end, search before deciding. If you stop here, you already have the thing most agent setups are missing.

Step 3 — Define a group

A group is the set of repositories you work on together. Author one with a member per repository:

$ camp group myproduct \
    --member api=~/code/myproduct-api \
    --member web=~/code/myproduct-web \
    --member infra=~/code/myproduct-infra

That writes ~/.config/camp/groups/myproduct.toml and wires session hooks into each member repository. If you would rather start from a commented template and fill it in by hand:

$ camp group myproduct --scaffold

Then re-run with --member flags once you have edited it. Two things to know: each repository belongs to exactly one group, and authoring refuses to overwrite an existing config unless you pass --force.

Working in a single repository? A group of one is fine, and still gets you workspaces and scoped memory. You can add members later by editing the TOML.

Step 4 — Open a workspace

A workspace cuts a git worktree in every member repository, all on a matching branch, and provisions each one. Create it with a slug describing the change:

$ camp new add-billing

Provisioning runs in the background. Check on it, and see the git state across every member at once:

$ camp status
$ camp list

Run a command in every member without visiting each directory:

$ camp foreach git status --short

When you are finished with the change, tear the whole thing down in one step:

$ camp remove --name add-billing

Workspaces are isolated, so you can keep several open at once and switch between them without them interfering.

Step 5 — Run a change through craft

Now start an agent session inside the workspace and let it run the arc of the change. The rituals are invoked as skills:

WhenInvokeWhat happens
The idea is still fuzzy/craft:brainstormThe agent interrogates it into a draft spec — problem, objectives, acceptance criteria, non-goals
The spec is drafted/craft:gauntletParallel adversarial passes attack it before it freezes
The spec is frozen/craft:planIt becomes an ordered set of independently committable slices
The plan is approved/craft:executeEach slice is built test-first by a dispatched subagent, with a conformance gate behind it
The work is built/craft:reviewA reviewer with no memory of how it was built reads the whole change against its intent

You do not need all of it. For a small, well-understood change, skip to /craft:execute. For a genuinely hard decision, /craft:consult convenes four reviewers — architecture, reliability, security, and user experience — and synthesizes their answers.

The plan is a starting point, not a contract. When a slice turns up something the plan did not anticipate, that is expected: the agent proves shaky assumptions before building on them and comes back to you rather than guessing.

Step 6 — Ship it

If your change spans several repositories, it becomes several pull requests that need to merge in the right order. That is what portage is for:

# in your agent session
/portage:pull_request create

That pushes every active repository, opens linked pull requests, and starts watching CI. Then /portage:pull_request monitor watches the checks, triages failures and review comments, and reports when everything is clean.

Nothing merges unless you authorize it. Merging is fail-closed: without auto_merge set in your group's release configuration, portage refuses to merge anything at all. Turning it on is a deliberate act. See the portage page before you enable it.

You will need the GitHub CLI (gh) authenticated, and GitHub is the only code host implemented today.

What the daily loop looks like

Once it is set up, a working day tends to go:

  1. Open a workspace for the change — camp new <slug>.
  2. Start a session in it and let the agent search the vault for what you already know about the area.
  3. Work the change, with the agent capturing decisions and dead-ends as it goes.
  4. Flush the session so what you learned outlives it — /lore:flush.
  5. Ship when it is ready, then tear the workspace down.

The compounding part is step 4. A vault that has been flushed consistently for a month is why the agent stops asking you the same questions.
