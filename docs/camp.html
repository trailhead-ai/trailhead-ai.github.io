Plugin

camp — multi-repo workspaces

One command opens a workspace spanning every repository in a group: a git worktree per repo, all on the same branch, provisioned and ready to work in. One command tears it down.

A real feature rarely lives in one repository. It touches the API, the client, and the shared schema package, and those are three checkouts, three branches with three chances to name them differently, and three sets of bootstrap steps before anything runs. Doing that by hand is tedious for a person and error-prone for an agent — the most common failure is not a bad edit, it is an edit made in the wrong checkout, or on the wrong branch, or in a tree that was never bootstrapped.

camp makes that unit — the set of worktrees a single change spans — a first-class thing with a name. You declare a group once: the repositories you work on together. From then on camp new <slug> creates a git worktree in every member repo on a branch derived from the slug, runs whatever provisioning steps you configured, and hands back one directory containing all of them. camp status answers “is it ready?” and camp remove takes the whole thing away.

camp is deliberately narrow about what it does not do. It never starts, stops, or replaces a process, and it never changes your shell’s directory on its own. It answers where to go and what to run, and a small shell wrapper acts on that answer. That boundary is why camp is safe for an agent to call: the worst it can do is print a path.

camp works without the other plugins and outside a harness session — it needs no lore vault and no craft ritual. It is not trailhead-free, though: the camp CLI locates a trailhead checkout by walking up from its own location, or via $TRAILHEAD_ROOT, and exits if it finds neither.

Key concepts

TermWhat it means
GroupA named set of repositories worked on together, declared in one TOML file. Each repository belongs to exactly one group — camp validates this and refuses to resolve a repo listed in two groups, naming both.
MemberOne repository in a group: a name, an absolute repo_root, an optional base branch (default origin/main), and optional named tasks.
WorkspaceThe whole multi-worktree unit for one slug — one directory holding a worktree per member, plus a manifest. Lives at state_dir("camp")/<group>/worktrees/<slug>/<member>.
SlugThe workspace’s name and address. Matches ^[a-z0-9-]+$; other input is normalized, with a notice on stderr. Path-traversal sequences and shell metacharacters are rejected outright, not normalized.
WorktreeOne member’s git worktree inside the workspace. A real checkout of that repo — git commands work normally in it.
Branch patternHow the slug becomes a branch name. Default worktree-{slug}, so slug login-rework gives branch worktree-login-rework in every member.
TaskA named, multi-step provisioning unit referenced per member. Steps are argv lists (never a shell string) with {repo_root} / {worktree} / {workspace} / {slug} placeholders. Carries phase (provision, the default, or activate), required (default false), and timeout_seconds. Completion is recorded per member in the manifest, so a task that finished ok is never re-run — only failed and never-run tasks execute.
Harness profileOptional [harness] block: doc_files (the workspace doc to write, default CLAUDE.md), binary (harness binary name, default claude — only its basename is read; camp does not launch it), inject (claude-hook or stdout), and pretrust (pre-seed Claude Code’s per-directory trust flag, default true).
Bookmark and refA durable named pointer from a workspace back to the harness session you were running in it. The ref is its short name (^[a-z0-9][a-z0-9._-]{0,63}$, defaulting to the slug); the store is global to the machine, so a ref resolves without knowing its group.
DriftDisagreement between the workspace manifest, git’s own worktree list, and the instance registry. camp doctor checks that consistency; camp status --json carries a drift block. See honest limits for what is a placeholder today.

Setting up a group

Group configs live at config_dir("camp")/groups/<name>.toml — on every platform including macOS that is ~/.config/camp/groups/<name>.toml. One file per group. You can write it by hand, but the CLI authors it for you:

$ camp group demo --member api=/Users/you/code/api --member web=/Users/you/code/web

That authors the config from the flags and wires the session hooks into each member repo. It refuses to overwrite an existing config unless you pass --force, and it verifies each repo_root exists and is a git repository unless you pass --allow-missing. camp group <name> --scaffold writes a commented stub for you to edit by hand instead (and wires no hooks); camp group <name> with no other flags re-wires hooks for a group that is already configured.

An annotated config

This is trailhead’s own group config, trimmed. Everything past [group] and [[members]] is optional.

# ~/.config/camp/groups/trailhead.toml
[group]
name = "trailhead"

[[members]]
name = "trailhead"
repo_root = "/path/to/trailhead"
# Named tasks this member opts into, referenced by name.
tasks = ["code-review-graph"]

[[members]]
name = "trailhead-ai.github.io"
repo_root = "/path/to/trailhead-ai.github.io"

[[members]]
name = "outpost"
repo_root = "/path/to/outpost"

[branch]
# Slug 'login-rework' becomes branch 'worktree-login-rework'.
pattern = "worktree-{slug}"

# A group-level named task. Steps are argv lists, run with shell=False.
# phase:           "provision" (on worktree creation and each SessionStart
#                  reconcile) or "activate" (on first `camp activate`).
# required:        false means a failure warns in `camp status` and continues.
# timeout_seconds: per-step subprocess timeout.
[tasks.code-review-graph]
phase = "provision"
required = false
timeout_seconds = 180

[[tasks.code-review-graph.steps]]
name = "build"
cmd = ["code-review-graph", "build", "--repo", "{worktree}"]

# Optional. Omit it entirely and camp uses the claude defaults:
# doc_files = ["CLAUDE.md"], binary = "claude", inject = "claude-hook".
# [harness]
# doc_files = ["AGENTS.md"]   # Codex, Copilot, Cursor read this instead
# inject = "stdout"           # universal floor; any [harness] block
#                             # without an explicit inject defaults here
# pretrust = false            # claude launches only

Task steps, and every other command in a group config, are author-trusted local input. camp runs them as argv lists with no shell, but sharing group configs from authors you do not trust is explicitly out of scope.

The workspace lifecycle

Create or enter. camp new <slug> is the single entry point for both. If no manifest exists for that slug it creates the workspace — a worktree per member on the pattern branch — and provisions in the background; if one does exist it re-enters without re-provisioning or clobbering anything. Either way the workspace’s absolute path is the only thing on stdout.

Check it. camp status with a slug resolvable from cwd or --name prints the per-member provision state — pending, ready, or failed — and exits with a code an agent can branch on: 0 all ready, 2 some pending, 3 some failed. Run outside any workspace it prints the fleet-wide table of every workspace, its branch, and its members, and exits 0. camp list (alias ls) prints slug and path, one per line, for scripting.

Provision and activate. camp setup re-runs outstanding work for a workspace — pending or failed members and any task not yet recorded ok. camp activate <member> runs that member’s activate-phase tasks and surfaces its workspace doc (CLAUDE.md by default) as context for the current session.

Work across members. camp foreach <cmd> runs a command in each member worktree with no shell interpretation, skipping members whose worktree is absent. --fail-fast stops at the first failure; --json gives a per-member result map.

Keep it current. camp sync fast-forwards canonical checkouts to origin/main and is safe by default — a dirty or off-main repo is skipped, not reset, unless you pass --force. camp rebase [--onto <branch>] rebases the workspace branches onto origin/main and stops with the conflicting repo named when a rebase conflicts. Both have real caveats today; see honest limits.

Tear it down. camp remove (alias rm) removes the workspace and its worktrees. It refuses on a dirty tree unless you pass --force, and it is guarded when the workspace still holds a bookmark. On success it clears that workspace’s bookmarks and prints the first member’s repo root — the place your shell should land, since the directory it was standing in no longer exists. On any failure, including partial removal, stdout is empty and the exit is nonzero.

camp never moves your shell — the wrapper does

Three verbs answer a question whose answer is a place: camp new (go here), camp remove (you can no longer stand there, go here instead), and camp resume (go here and run this). camp prints those answers and stops. Acting on them — the cd, and for resume the launch of the harness — needs a shell function, which is what the trailhead shellenv line installs:

$ eval "$(/path/to/trailhead/bin/trailhead shellenv)"
# add that to your shell profile — fish, zsh, and bash are all handled

The wrapper it defines intercepts those three verbs and acts on what camp printed. Without it, camp resume refuses outright rather than printing two lines that look like success and do nothing. camp new and camp remove still do their work and print the path, but nothing takes you there — they add a one-line tip on stderr pointing at the shellenv line. If a camp command tells you the shell integration is not active, this is the fix.

camp resume replaces your shell’s foreground process. A user runs it in their own shell — an agent should relay the command, not run it on the user’s behalf.

Bookmarks

A bookmark is a durable named pointer from a camp workspace to the harness session you were running in it — what turns “pick this back up next week” into one command. Capture is cwd-scoped: run it from inside the workspace you want to keep, and the ref defaults to that workspace’s slug.

$ camp bookmark --ref login --note "waiting on the schema PR"
$ camp bookmark ls
$ camp resume login
$ camp bookmark rm login

A workspace holds at most one bookmark. Re-capturing under the same ref updates it in place; re-capturing under a different ref is refused, naming the existing one, because dropping a bookmark is always explicit. A ref already held by another workspace is refused rather than stolen.

ls, rm, and resume address a ref, so they work from any directory including outside every group. camp bookmark ls lists every bookmark on the machine, most recently updated first, and marks rows that need attention: [workspace gone] or [transcript gone] when the bookmark points at nothing (the fix is rm), and [expires ~Nd] when the harness’s own transcript retention is closing in. Bookmarks outlive that retention window — after cleanup a bookmark is a pointer to nothing.

Hooks camp writes into your repos

Wiring a group modifies files in your repositories, so it is worth knowing exactly what changes. camp group writes a SessionStart hook entry into each member repo’s .claude/settings.json, invoking camp’s own session-bootstrap handler. Each workspace additionally gets its own .claude/settings.json with a SessionStart hook that reports provision status, and — when the inject strategy is claude-hook — a PostToolUse hook that loads a member’s doc silently into context mid-session instead of dumping it to the log.

The writes go through a JSON load-and-dump, never string templating: unrelated keys are preserved, paths with spaces or quotes round-trip, and re-running adds no duplicate entries. The command is written as ${CAMP_BIN:-<absolute path>} so you can override the binary without editing settings files.

Command reference

Every command below is verified against camp --help and the CLI source. --group <name> works on any group-aware command to target a group from outside it; --dry-run (or CAMP_DRY_RUN=1) prints what camp would execute without running it.

camp pwd <slug>Print a workspace path — exactly one line on stdout, safe for cd "$(camp pwd <slug>)".
camp group <name> [--member NAME=PATH] [--branch-pattern P] [--scaffold] [--force] [--allow-missing]Author a group config and wire hooks.
camp list [--json]List all workspaces. Alias ls.
camp status [--name <slug>] [--json]Per-member provision state (exit 0/2/3) or the fleet table.
camp activate <member> [--name <slug>]Run a member’s activate-phase tasks and surface its workspace doc.
camp setup [--background] [--json]Provision or retry members and outstanding tasks.
camp remove [--force] [--name <slug>]Tear a workspace down. Alias rm.
camp sync [--force] [--json]Fast-forward canonical checkouts to origin/main.
camp rebase [--onto <branch>] [--name <slug>]Rebase the workspace branches.
camp foreach [--fail-fast] [--json] <cmd>Run a command in each member worktree.
camp bookmark [--ref <ref>] [--note <text>]Bookmark this workspace’s harness session.

A worked example

Two repositories, one change spanning both.

# 1. Declare the group, once. Writes ~/.config/camp/groups/demo.toml
#    and wires the SessionStart hook into both repos.
$ camp group demo --member api=/Users/you/code/api --member web=/Users/you/code/web

# 2. Open a workspace. With the shellenv wrapper active this also cd's you in.
$ camp new login-rework
camp new: created workspace 'login-rework' — provisioning in the background
  check provisioning: camp status login-rework
  activates when ready, or run: camp activate login-rework
/Users/you/.local/state/camp/demo/worktrees/login-rework

# 3. Both repos are checked out on worktree-login-rework, side by side.
$ ls
api  web

# 4. Is it ready? Exits 0 all ready, 2 some pending, 3 some failed.
$ camp status

# 5. Work normally — these are ordinary git checkouts.
$ camp foreach git status --short

# 6. Stopping for the week? Name the session so you can come back.
$ camp bookmark --ref login --note "waiting on the schema PR"
$ camp resume login

# 7. Done. Refuses on a dirty tree without --force, and returns you
#    to the group repo because the directory you were in is gone.
$ camp remove

Honest limits

camp is in daily use, and these are the sharp edges worth knowing before you plan around it.

The shell wrapper is not optional in practice. Without eval "$(trailhead shellenv)" in your profile, camp resume refuses to run at all, and camp new and camp remove leave your shell wherever it was. This is the most common source of confusion with camp.

Dev-environment orchestration is deferred. There is no [dev_env] capability in the group config and camp’s doctor carries no dev-env probes. Provisioning is what you write into tasks, nothing more.

camp sync is narrower than it reads. Today it fast-forwards trailhead’s own canonical checkout rather than every member of your group; operating on group members is future work.

camp rebase delegates to a helper script that is not shipped in the repository today, so it fails with a “rebase script not found” error unless you supply one. Rebasing member branches by hand, or via camp foreach, works fine in the meantime.

Registry-drift detection is a placeholder. Nothing writes the instance registry yet, so the drift block in camp status --json is always empty and camp doctor’s consistency check always reports no drift. The manifest and git-worktree halves of that check are real.

Claude Code is the only harness implemented. Harness profiles do support AGENTS.md-style doc files and a stdout injection floor that works with any tool, but the session hooks and the trust pre-seed are Claude Code integrations.
