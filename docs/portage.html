Plugin

portage — shipping

Get the change merged. portage treats every pull request a camp group opens as part of one release: pushed together, watched together, triaged together, merged in the order you declared.

A change that spans three repositories is not three independent pull requests. It is a stack: the shared library has to land before the service that consumes it, the service before the client. Each PR has its own CI run, its own review comments, its own merge conflicts appearing at different times. Merging them in the wrong order breaks the build for everyone else, and at GitHub that is irreversible.

The manual version of this is polling. You push, you wait, you check three tabs, one job fails on a flake, you rerun it, a reviewer comments on the second PR, you fix it and push, which invalidates the first PR’s green run. Hours of attention spent on a loop that is almost entirely mechanical, punctuated by a handful of real judgment calls.

portage moves the loop off your desk. It reads the repository set from your camp group, pushes every active repo, opens and cross-links the PRs, then hands off to a background agent that blocks on CI, dispatches a fixer when something breaks, and merges the stack in dependency order once everything is clean. The judgment calls — is this review comment right, is this failure real — still get made by a model reading the actual content; the polling does not consume your context or your time.

portage is camp-group-shaped. It reads its repository set from the camp group manifest, and every command takes a --manifest path or derives one. It is not a general-purpose PR tool you can point at an arbitrary repository — if you are not working inside a camp workspace, portage has nothing to operate on. A group of one repository works fine; a checkout with no group does not.

What you need

  • The gh CLI, authenticated. Every read and write to the code host goes through gh. Without it, nothing in portage works.
  • A camp group and an active workspace. The manifest is the input.
  • The trailhead checkout. portage ships a portage CLI, but its bootstrap resolves the shared trailhead library by walking up from its own location to the checkout (falling back to $TRAILHEAD_ROOT). With neither available it exits with a legible error rather than running. The CLI is on $PATH through trailhead’s shim directory once eval "$(trailhead shellenv)" is in your shell profile.

The pull_request skill

portage exposes one skill, /portage:pull_request, taking a verb as its first argument. The skill itself is thin — it parses the verb and dispatches subagents, so the expensive work happens in isolated contexts rather than in your session.

VerbWhat it does
createReview the diff, then push and open a PR for every active repo in the group, cross-link the siblings, write the sidecar, and start watching CI
updateRe-run local checks, push new commits to the PRs that already exist, and resume watching
monitorWatch CI on the open PRs, triage failures and reviewer feedback, and merge once every PR is clean
mergeMerge the open PRs in dependency order right now, skipping the watch loop — for when you already know they are green

create and update both end by launching the same background monitor that monitor runs, so in practice you invoke the skill once and get told when the stack has merged or when it needs you.

Four old skill names are retired. /portage:open, /portage:update, /portage:monitor, and /portage:merge no longer exist — they are gone, not aliased. Use /portage:pull_request create, update, monitor, and merge instead.

The four subagents

updater — the push orchestrator

Mechanical, no judgment. It runs a fixed linear flow: detect the active repos from the manifest, preflight each one in parallel (everything committed, commits GPG-signed with conventional prefixes, branch pushable without clobbering anyone), push, open or update the PRs, cross-link siblings in each PR body, and write the prs.json sidecar. It returns a short report ending in a pr_pairs line the caller needs to launch the monitor. Every member of the group is a peer — there is no privileged repo with a different push path.

It deliberately does not launch the monitor itself: a background agent dispatched from inside a subagent loses its notification channel when that subagent returns, so the monitor has to be launched from the top-level session.

monitor — the watch, fix, and merge operator

The one that runs for hours. It blocks on portage wait-for-actionable, which polls every 30 seconds and returns only when something needs a decision, then handles the action it was handed: done moves on, rebase and rerun_ci run the commands the evaluator supplied, and fix_ci and review dispatch the green driver. It never merges a PR whose last commit came from a fix cycle that has not reported ready, and it gives up after three fix cycles on the same PR without progress — at which point it dispatches the summarizer to write the blocker report and stops.

When every PR reports done, it calls portage merge once, cleans up each repo back to main, and updates the sidecar. It does not use gh pr merge --auto, deliberately: the explicit merge call is what keeps ordering and post-merge cleanup under its control.

green-driver — drives one PR to green

Handed a single fix_ci or review action, it triages, fixes, pushes, and re-reviews until it can return ready or blocked. On a CI failure it sifts the annotations for the actionable lines, fixes the code, pushes, and then runs a fresh code review over its own diff — a fix written from CI output is never trusted as clean without one. If triage stalls on something that looks flaky or unexplained, it escalates to a root-cause pass instead of guess-and-push, because every wasted attempt burns one of the monitor’s three cycles.

This agent is the default behind the swappable [release].green_driver_agent seam. The monitor dispatches whatever name that key resolves to, so a group can substitute its own fixer without touching the monitor. The name is verified before the watch loop starts: if no installed subagent matches, the monitor stops with a named config error rather than discovering the problem mid-loop.

summarizer — the cheap brief

Runs on Haiku. Given a repo path and a PR number it fetches metadata, diff, and inline comments through portage summarize and returns a compact structured brief — what the change does, the shape of the diff, review feedback grouped by author with the bot called out separately, CI state, and anything gating merge. It exists so the rest of the system can understand a PR without loading its full diff and comment thread into an expensive context.

Configuration

Per-group behavior lives in the [release] block of your camp group TOML. Every key is optional, and the defaults are the conservative ones.

# ~/.config/camp/groups/<group>.toml

[release]
# Dependency order for a multi-PR merge, by camp member name.
# Required whenever more than one PR is queued.
merge_order = ["shared-lib", "service", "web-client"]

# Standing authorization to merge. Fail-closed: without this,
# `portage merge` refuses everything.
auto_merge = true

# Login whose review comments count as actionable. Omit for
# CI-only evaluation — no review action is ever emitted.
review_bot_login = "my-review-bot"

# Agent the monitor dispatches on fix_ci / review actions.
# Defaults to portage's own `green-driver` when absent.
green_driver_agent = "green-driver"

# Reserved field — see the note below.
# external_tracker = { kind = "..." }
KeyDefaultEffect
merge_ordernoneList of camp member names giving merge order. With more than one PR queued and no order declared, portage merge refuses. A single PR needs no order.
auto_mergefalseMust be exactly true for any merge to happen. See below.
review_bot_loginnoneWhose comments count as actionable review. Absent means CI-only — the evaluator emits no review action until a human comments.
green_driver_agentgreen-driverWhich installed subagent handles fix_ci and review. Verified to exist before the watch loop starts.
external_trackernullReserved for an issue-tracker connector. No connector ships today — the field is read, defaults to null, and every tracker transition is a no-op.

auto_merge is fail-closed, and that is the whole safety story. If auto_merge is unset or false, portage merge refuses to merge anything — before any call to the code host, regardless of how many PRs are queued or how clean they are. It exits 2 with a message naming the remediation, and the monitor is instructed to stop there rather than retry or work around it. Nothing merges automatically until you have written auto_merge = true into the group TOML yourself. The check lives in the merge implementation, not in agent prose, so it holds even if an agent misreads its instructions.

The corollary is worth stating plainly: with auto_merge = true, a PR reporting done is merge-eligible as it stands. There is no separate human-approval gate in the loop. Enable it when you want the group merged unattended, and lean on branch protection if you want a human in the path.

Note that the approval signal is never applied by portage. Neither the monitor, the green driver, nor the updater may post an approving review or apply a human-approved label — that signal is human-authored only. portage approvals exists as a read-only query for whether such a signal exists on a PR’s current head, but it is not part of the merge path.

The prs.json sidecar

The updater writes a small file next to the camp manifest, at <manifest_dir>/prs.json:

{
  "schema_version": 1,
  "prs": [
    {"repo": "shared-lib", "pr_number": "42",
     "url": "https://github.com/acme/shared-lib/pull/42",
     "branch": "worktree-feat"}
  ],
  "external_tracker": null
}

It exists so the association between a workspace and its pull requests survives the session that created them. Without it, every later step would have to rediscover the PR numbers by listing PRs by branch on each remote — a slower, network-dependent guess. The sidecar is owned by portage, sits alongside camp’s manifest rather than inside it, and is written atomically at mode 0600. Any step that needs the association can read it back with portage sidecar read.

CLI reference

The agents drive these; you can run them directly too. The evaluator commands (check-status, evaluate-status, wait-for-actionable) print JSON on stdout including errors, because callers parse them. The orchestration commands (detect-repos, merge) report errors as exit codes plus stderr — exit 2 for a config or manifest failure, exit 1 for a partial merge.

CommandWhat it does
portage detect-repos --manifest PATHReport the active repos in the workspace as JSON. Members whose worktree is gone are skipped, not fatal.
portage check-status REPO PRPoll one PR’s raw status. Takes --since and --review-bot-login.
portage evaluate-status REPO PRTurn that status into a recommended action. Also takes --fail-count.
portage wait-for-actionable REPO:PR...Block until at least one PR is actionable. Takes --since, --timeout, --interval, --review-bot-login.
portage merge --manifest PATH [--toml PATH] PAIRS...Merge in dependency order with the safety gates. Pairs are path:pr_number:member_name.
portage approvals REPO PRRead-only: does a human-authored approval exist for the current head? Exit 0 approved, 1 not (including stale), 2 on error.
portage summarize REPO PRFetch metadata, diff, and comments through the VCS boundary with untrusted text marked.
portage sidecar read|write --sidecar PATHRead or write the prs.json sidecar. write takes a repeatable --pr repo:number:url:branch.

A worked run

You have finished a change spanning three repos in a camp workspace. In your agent session:

/portage:pull_request create

The skill reviews the diff with you, then dispatches the updater. It detects the three active repos, preflights each in parallel, pushes, opens three PRs, cross-links them, and writes the sidecar. It hands back the PR URLs and the pr_pairs line. The session launches the monitor in the background and tells you it will notify you when the stack merges or needs attention. You go do something else.

The monitor blocks on wait-for-actionable. Twenty minutes later the service repo’s test job fails; the evaluator returns fix_ci with the failing checks attached. The monitor dispatches the green driver, which sifts the annotations, fixes an assertion, pushes a signed conventional commit, runs a fresh review over its own diff, and reports ready. The monitor loops. Later a reviewer comments on the client PR; that comes back as a review action and takes the same path.

When all three report done, the monitor merges in the declared order:

portage merge \
  --manifest ~/.local/state/camp/acme/worktrees/feat/manifest.json \
  --toml ~/.config/camp/groups/acme.toml \
  /path/shared-lib:42:shared-lib \
  /path/service:17:service \
  /path/web-client:9:web-client

The command checks auto_merge first and would refuse outright if it were unset. It is set, so the three PRs merge in order, JSON comes back listing merged, failed, and skipped, and the exit code is nonzero if anything did not land. The monitor resets each repo to main, updates the sidecar, and you get a notification saying the stack is merged.

If auto_merge had been left off, the run reaches exactly the same point and stops there, telling you all three PRs are ready and naming the one line to add if you want it to merge next time.

Reviewer and CI text is data

Everything a hostile CI run, review bot, or PR author can write — annotation messages, review bodies, PR titles and descriptions, diffs, inline comments — crosses into the agents through a single boundary that wraps it in an escaped untrusted-content marker. The escaping means the wrapped text cannot terminate the marker early or forge a fresh trusted frame around itself.

The agents are instructed to read anything inside that marker as a claim about the code, never as an instruction to execute. If a comment says to approve, to merge, or to ignore the rules, that is reported as a suspicious comment rather than obeyed. This matters more than usual here: portage runs unattended for hours against text written by third parties, and a CI action is not a trusted narrator.

Honest limits

GitHub is the only code host implemented. The provider sits behind an interface with a single-entry registry, and adding a backend is documented as implementing a subclass plus one registry line — but GitLab, Bitbucket, and everything else are an extension point, not shipped support. Asking for any other provider raises an error naming the registered ones.

No merge lock. Two concurrent merges against the same group are not guarded. Solo use makes the race unlikely; it is a known residual, not a solved problem.

No issue-tracker connector. external_tracker is a reserved field. It is read, defaults to null, and every transition it would drive is a no-op today.

The fix loop gives up at three cycles. Three attempts on one PR without progress and the monitor stops with a blocker report. That is a deliberate bound on wasted work, not a failure it will keep grinding at.

Self-approval is not structurally prevented. No portage component may apply the approval signal, and none does — but automation running under your own credentials could. That residual is accepted within single-operator scope; branch protection is the answer if you need more.
