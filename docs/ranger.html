Plugin

ranger

Unattended drains over a camp group’s task queue. One drain shapes every open task until it is runnable; the other builds every runnable task in its own workspace and pushes it to a pull request. Both run inside bounds you set, and both leave a durable report behind.

craft gives you rituals that are excellent per task — refine one task until it is executable, build one plan slice by slice, review one change against its intent. Each of those rituals needs an operator: someone to name the task, watch the agent, and decide what happens next. That is fine for the change you are actively thinking about, and it is the bottleneck for everything else. A backlog of thirty shaped tasks does not need thirty sessions of your attention; it needs someone to turn the crank.

ranger is the crank. It takes a backlog that already exists in your lore vault, derives which tasks are actionable right now, and runs craft’s ritual against each one in a dispatched agent that has no channel back to a human. The work happens in parallel up to a bound you set, each result lands in a file, and the run ends with a report naming what got promoted, what got built and pushed, and what came back needing you. Overnight, a shaped backlog becomes a set of merged pull requests and a triage list.

The word shaped is doing real work in that sentence. Ranger does not invent tasks, decide what is worth building, or choose priorities. The tasks must already be records in the vault — captured by you, by an agent during a session, or by a planning ritual. Ranger runs the backlog you already have; it does not produce one.

The two drains

The refine sweep — /ranger:refine

The shaping drain. It derives every standalone task in the elected vault that is open, or blocked with an operator’s answer recorded on it, and pushes each one through craft’s refine ritual: draft a Delivers list, a test contract, and a Files payload from the code and the vault, cite every derived answer, and promote the task to ready. Standalone means childless and parentless — a task with children is a plan and belongs to a planning ritual, not to a sweep.

Dispatch runs a pool of up to four agents at once, each with its own ten-minute deadline, so one confused agent expires alone rather than stalling the sweep. A task that has already escalated and is still waiting for an operator is never re-dispatched; it is reported once and left alone until an answer appears on the record.

Set your expectations for what comes back. A real backlog produces a lot of escalation, because the ritual refuses to invent answers to questions only you can settle. The first measured drain of twelve tasks promoted five, escalated three, routed three, and left one blocked. A sweep’s product is a triage list, not a ready queue — and the report hands you the exact command to answer each parked question.

The execute drain — /ranger:execute

The building drain. It derives every standalone task the vault reports as runnable — status ready, every dependency done — and further filters to the ones whose Files payload actually names a member-repo file, so a task refined to touch only its own record is parked rather than dispatched to build nothing. Each surviving task gets its own ephemeral camp workspace, provisioned from a freshly synced base, and its own dispatched agent running craft’s execute ritual inline: tests first, GPG-signed commits, review, then a push.

A pushed branch is handed to portage, which opens the pull request, watches CI, triages failures, and merges under the group’s standing authorization. The coordinator writes every task status edge itself — the run claim at dispatch, done the moment the push lands, blocked when the agent parks a question — because a status split across a process boundary races.

An agent that hits a real decision does not guess. Both rituals end at an escalation contract: when a question survives the self-serve resolution passes, the agent writes it onto the task record and returns ESCALATED or BLOCKED. It never asks — there is no human on the other end of a dispatched agent, so a question asked is a run that hangs — and it never picks an answer to keep moving. Escalation is a normal, expected outcome, not a failure mode.

The CLI owns the state, not the transcript

This is the architectural rule worth stating plainly, because everything else about ranger follows from it. The ranger CLI owns everything mechanical: preconditions, the per-vault lock, queue derivation, outcome parsing, the in-flight bookkeeping, and the report. Its files — not the coordinating agent’s transcript — are the drain’s state.

The coordinator never reads a task record. Not its body, not its question, not its payload, not its diff. It never reads a dispatched agent’s reply as a result either. Results travel in outcome files: the agent writes one line to a path it was handed, and the CLI reads that file and buckets it. The coordinator’s whole job is to dispatch, tell the CLI to record, and move on.

That is containment by design. A reply is text you cannot un-read, and a coordinator that parses one has just pulled a task’s citations, file paths, and reasoning into the context the dispatch existed to protect — multiplied by every task in the queue. It is also why a drain survives interruption: the report and the state file next to it are re-rendered from durable state on every write, so a coordinator that dies mid-run leaves a valid partial report on disk, a lock naming its holder, and enough labels on the task records for the next run to pick the work back up.

Key concepts

The queue and its buckets

A queue is derived, never stored. Each derivation reads the vault fresh and sorts every candidate into exactly one bucket, and the bucket decides what the coordinator does. Two of the sweep’s four buckets are reported and never dispatched, which is the churn guard that keeps an unanswered escalation from being re-attempted every pass.

skipped:collisionIts workspace slug is already claimed by another task

The elected vault

A drain runs from inside the camp group’s workspace, and both the group and the vault are resolved from the current working directory. There is no --group flag. The vault comes from the group’s lore_scopes binding, and if that resolution falls through to lore’s unconditional default vault the drain refuses to start — draining the default vault when you meant your group’s vault would rewrite a pile of unrelated records unattended, and nothing downstream would notice. Running from the wrong directory is a refusal, not something to override.

The lock and its token

At most one drain runs per vault. The lock file is created with O_CREAT | O_EXCL, so the OS decides the race, and its body names the group, the holder pid, the host, and a start time. Ranger never removes another process’s lock and never reaps a stale one automatically — a held lock is a refusal that names the live holder, or, when the holder’s pid is gone, prints the exact rm command for you to run yourself.

Releasing needs the lock_token that start minted and returned. The vault name identifies the lock; the token identifies the run. Without it, a mistyped or out-of-order finish would tear down a sweep that is still going.

--holder-pid

A drain is not one process — it is a coordinator driving a series of short-lived CLI invocations. --holder-pid names the long-lived process whose liveness is the drain’s liveness, and it is what the lock records. The default is ranger’s own parent, which is correct only when that parent drives the run to completion; under a harness that spawns a fresh shell per command it dies the instant start returns and the drain reads as abandoned to its own next verb. Coordinators pass their own pid explicitly.

The three bounds

All three are flags on ranger drain start. The refine sweep exposes none of them: its pool is fixed at four agents with a ten-minute per-slot deadline.

FlagDefaultWhat it bounds
--concurrency N2Executor agents building at once
--inflight-cap N3Pushed-but-unmerged tasks holding a monitor slot; dispatch pauses at the cap
--monitor-deadline HOURS2How long one monitor slot may stay in flight before it is reclaimed

The in-flight cap is the one people underestimate. It counts tasks that have been pushed but not yet merged — work sitting in a pull request waiting on CI, on branch protection, or on you. Without the pause, an unattended drain opens unbounded unmerged PRs against a gate only a human can clear. The count is tracked durably by the CLI, not in the coordinator’s head, so it survives a restart; a slot whose deadline passes is reclaimed into a distinct monitor-timeout bucket and its workspace is preserved, because an expired deadline means the loop lost track of the PR, not that the work is disposable.

The outcome file

Every dispatched agent writes exactly one line to a path it was handed, and that line is the entire result of its run. The grammar is closed, and the CLI parses it — anything outside the grammar, including commentary, is bucketed as a failure with the raw line carried into the report as the reason. A missing or empty file is the crash signal: the agent died, timed out, or never ran.

WriterTokens
refine agentPROMOTED · ESCALATED · ROUTED <target> · SKIPPED <reason>
execute agentPUSHED <branch> <sha> <diffstat> · BLOCKED <reason> · FAILED <reason> · SKIPPED <reason>
portage monitorMERGED · READY <reason> · BLOCKED <reason> · STOPPED <reason>

Degraded mode

Portage’s presence is the one precondition that is a flag rather than a refusal. When it is absent, drain start reports degraded: true and the drain runs without the parts portage would have driven: no pull-request tail, no monitor, and no in-flight cap. A PUSHED task is done at the push, its workspace is torn down there rather than at a merge, and the report carries a banner saying so.

The report

Every run writes a timestamped markdown report under ranger’s state directory, keyed by group, with a JSON state file beside it. The report is re-rendered in full from that state on every append, written to a temp file and renamed into place, so it is a valid partial artifact at every moment — including when a run dies before finishing. Recording the same task twice is a no-op.

A sweep’s report buckets are promoted, escalated-awaiting-operator, routed, blocked-answered, blocked-still-waiting, skipped, and failed; the two waiting buckets carry the task’s question and a ready-to-paste command that answers it. A drain’s buckets are pushed, blocked, failed, crashed, skipped, and dropped, where pushed carries one of four substates: merged, in-flight, awaiting-human-approval, or monitor-timeout. Question text and record bodies are lifted by the CLI directly out of the record, so they reach the report without transiting the coordinator’s context, and every untrusted field is scrubbed for credential patterns on the way in.

What ranger needs

Ranger is the least standalone plugin in the suite, and it is worth being blunt about that. It drives the other tools; it does not replace them.

  • The trailhead checkout. Ranger reaches camp as a library import and craft’s procedures as files under the composed install tree.
  • A camp group, resolvable from the directory you run in. Absent, the drain refuses.
  • A lore vault elected for kind task by that group’s lore_scopes binding, and above the default floor.
  • craft, installed, because the ritual document each dispatched agent reads is craft’s. No craft, no drain.
  • A resolvable committer email, from LORE_EMAIL or git config --global user.email. This is checked at startup rather than left to fail mid-ritual, where a dispatched agent with no one to ask has been observed inventing one.
  • portage, for the pull-request tail. Optional, and its absence is degraded mode rather than a refusal.

All four hard checks run before the lock is taken and before anything is written, so a failed precondition leaves the filesystem exactly as it found it. Each failure prints its own one-line remediation.

The safety story

An unattended loop that can commit, push, and merge deserves scrutiny. Four things bound it:

  • Bounded concurrency. At most --concurrency builds run at once, and each holds one ephemeral workspace that no other task can claim.
  • A cap on unmerged work in flight. Dispatch pauses at --inflight-cap, so the drain cannot pile up pull requests faster than they clear.
  • A deadline on every watch. Each monitor slot expires after --monitor-deadline hours into a named bucket, with its workspace preserved for inspection.
  • Merging still runs through portage. Ranger never merges anything itself. Merges go through portage merge, whose auto_merge check in the group’s [release] config is fail-closed: unset or false and it refuses to merge, before any call to the host, regardless of how clean the PRs are.

On top of that, no component of the drain applies the approval signal — not the coordinator, not the executor agent, not portage’s agents. A gate that the automation building the change can open is not a gate. Agent-written text never reaches a shell as part of a command string: outcomes travel by file, and a branch that is not the workspace’s own worktree-<slug>, or a sha that is not a hex object name, is refused rather than recorded.

A worked example

Start inside the camp group’s workspace — that is what elects the vault. Shape the backlog first, then build what shaping produced.

# in your harness, from inside the group's workspace
> /ranger:refine

# the coordinator drives the CLI; you watch the per-task lines go by
#   12 tasks derived
#   task/parser-error-spans   promoted
#   task/retry-backoff        escalated
#   ...
# and it hands back a report path plus the bucket counts

Read the report. Every escalated and still-blocked line carries the question and the exact command that answers it, so triage is a pass down that list. Answer what you can, then build:

> /ranger:execute

# or, with wider bounds, tell the coordinator what to pass:
> /ranger:execute with --concurrency 4 --inflight-cap 5

Each buildable task gets a synced base, its own workspace, its own agent, and a pushed branch that portage takes from there. Tasks flip to done as their pushes land, PRs merge under the group’s auto_merge authorization, and the final report tells you which workspaces are still standing and why. If you want to see the queue without committing to a run, derive it directly:

$ ranger queue derive --vault my-vault --actionable

Honest limits

Ranger runs a shaped backlog, not an empty one. Tasks must already exist as records in the vault. Ranger derives, classifies, and drains — it does not decide what is worth doing, and it never invents work.

Escalation is the common outcome, by design. Roughly half of a real backlog comes back needing you. That is the ritual refusing to guess, which is what makes the other half trustworthy — but read “drained” as “triaged”, not “finished”.

GitHub is the only code host implemented. This reaches ranger through portage. Without a host, the drain still builds and commits; it just has no pull-request tail.

Claude Code is the only harness implemented. The dispatch model ranger depends on — background subagents with their own contexts — is wired through trailhead’s harness seam, but only one harness is shipped today.

Only standalone tasks are drained. A task with children is a plan and a task with a parent is a slice; both belong to craft’s planning and execute rituals, not to a drain.

One drain per vault, and no automatic recovery. A stale lock is reported with the removal command, never cleared for you. A run that dies leaves preserved workspaces and tasks marked in-progress for the next run’s resume ritual to pick up.
