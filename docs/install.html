Getting started

Installing Trailhead

Trailhead installs by cloning the repository and running one command. There is no package to download, no remote fetch, and no pip install step — the checkout is the source.

Let your agent do it. Trailhead ships an install guide written for agents. Tell yours: “Read https://github.com/trailhead-ai/trailhead/blob/main/INSTALL.md and set trailhead up for me.” It works through the guide with you step by step: it checks your prerequisites, asks which plugins you want, installs them, puts the CLIs on your PATH, makes sure the machine has a GitHub login, sets up Outpost and keeps it running, joins or creates your lore vaults, lets the machine sign vault commits unattended, and finishes only when trailhead doctor reports the host ready. Every step is safe to re-run, so it also brings a half-configured machine the rest of the way.

Requirements

  • Python 3.11 or newer. Trailhead has zero third-party runtime dependencies — the standard library is all it needs. Your system python3 may well be older than 3.11; check with python3 --version before you start.
  • git, with your identity set. Used for the checkout and for the memory vault, which is itself a git repository. lore commits to the vault as you, so git config --global user.name and user.email must both be set.
  • tmux. Every camp workspace runs in its own tmux session.
  • A supported shell — bash, zsh, or fish.
  • An agent harness. Claude Code is the harness that ships today. Trailhead detects it by the presence of a ~/.claude directory.
  • The GitHub CLI (gh), authenticated. portage uses it to open, watch, and merge pull requests, Outpost’s setup uses it to clone its repository (which is not public: setup works only for accounts that have been given access), and it is the usual credential for syncing lore vaults with their remotes.
  • Node 22 or newer, and npm, for building and running the Outpost daemon.

Install

Clone the repository somewhere permanent and run the installer. Where you put the checkout matters a little: it stays on disk and remains the source of everything trailhead installs, so pick a location you are not going to clear out.

$ git clone https://github.com/trailhead-ai/trailhead.git
$ cd trailhead
$ ./bin/trailhead install

With no flags, install auto-detects your harness, installs every agent-plugin — lore, camp, craft, portage, outpost, and trailhead, a small one that tells you at the start of a session when your install is behind its source — and builds command-line shims for the plugins that ship a CLI. It prints a summary of what it did and what you still need to do.

Here is what happens under the covers, in order:

  1. Detect harnesses on the machine.
  2. Resolve the effective config — the config file (default config/default.toml) merged with any command-line overrides, producing the set of harnesses, plugins, and individual subagents and skills to install.
  3. Compose and wire each harness under a lock: build the selected plugin trees, then register them with the harness.
  4. Build the CLI shim directory — one small wrapper per CLI-bearing plugin, each pointing back at your checkout.
  5. Install the user-level rules that the wired plugins ship, into each harness.
  6. Bootstrap lore — create the default vault as a git repository, seed its config, and install the vault write guardrail. This step is idempotent, and if it fails the whole install fails rather than leaving you half-configured.
  7. Register the core vault — copy the checkout’s bundled core-vault/ into trailhead’s own state directory and register it with lore as core, a read-only, trusted vault. This step prints one line saying what it did and never fails the install; if a vault named core already exists and is not trailhead’s copy, it declines and says why.
  8. Print the summary.
Trailhead does not edit your shell profile. It is brew-style: the installer tells you the line to add, and you add it. The next section is not optional — without it, none of the plugin CLIs will resolve.

Put the CLIs on your PATH

Add this line to your shell profile, using the absolute path to the checkout you just cloned:

eval "$(/absolute/path/to/trailhead/bin/trailhead shellenv)"

Then restart your shell, or re-evaluate the line in the current one. shellenv detects your shell from $SHELL; pass --shell fish, --shell zsh, or --shell bash to override it. For fish, the profile is usually ~/.config/fish/config.fish; for zsh, ~/.zshrc; for bash, ~/.bashrc.

What that one line sets up:

  • TRAILHEAD_ROOT, pointing at your checkout.
  • The shim directory on your PATH, so lore, camp, and portage resolve.
  • A trailhead shell function that re-resolves itself from the profile line at every shell startup. This is why moving or re-cloning the checkout only requires editing that one line — you do not need to re-run the installer.
  • A camp wrapper function for camp remove. Removing a workspace from inside it deletes the directory your shell is standing in; camp prints the group’s first member repo as the place to go, and the wrapper takes you there. Without it, camp remove still does its work and prints the path, but leaves you where you were. camp new needs no wrapper — it hands your terminal to a tmux session already rooted in the workspace.

Finally, start a fresh agent session so the harness picks up the newly installed plugins. An already-running session will not see them.

Verify

trailhead doctor prints a read-only report: what is installed, where it was installed from, and whether this machine is ready to use. It never changes anything. The report ends with one verdict line, HOST READY or HOST NOT READY, and that line is the answer — doctor always exits 0, so read the verdict, not the exit code.

$ trailhead doctor
trailhead doctor (read-only report):

  claude_code:
    marketplace: trailhead (registered)
    installed: camp, craft, lore, outpost, portage, trailhead

  CLIs on PATH:
    lore: /Users/you/.local/state/trailhead/bin/lore
    camp: /Users/you/.local/state/trailhead/bin/camp
    portage: /Users/you/.local/state/trailhead/bin/portage
    outpost-gateway: /Users/you/.local/state/trailhead/bin/outpost-gateway
    trailhead: /Users/you/.local/state/trailhead/bin/trailhead (note: a pip-installed trailhead earlier on PATH can shadow the shellenv function)
  shim dir: /Users/you/.local/state/trailhead/bin (present)
  python3: Python 3.12.3

  install provenance:
    checkout: /Users/you/code/trailhead
    wired at: 9c3e1b7d2a4f6e8c0b1d3f5a7c9e2b4d6f8a0c1e (2026-11-13T16:48:47Z)
    last update check: ok (2026-11-16T09:12:05Z)

  host readiness:
    [ok] forge:default: reachable from this shell (the background service's access is not checked)
    [ok] outpost: Outpost is configured and built
    [ok] vault:default: vault default is a git repository with a remote and is synced
    [ok] signing: this host signs unattended (key 256 SHA256:… you@laptop (ED25519))
    [ok] author: this host makes vault content
    [missing] supervisor: no supervisor entry keeps Outpost running
      fix: trailhead outpost enable
      (INSTALL.md step 7)
  HOST NOT READY: 1 missing, 0 could not be checked

Every [missing] item prints a one-line fix: you can run as shown, and names the step of the agent install guide it belongs to. Run each fix and re-run doctor until the verdict reads HOST READY. An item doctor could not confirm, usually a remote it could not reach, shows as [could-not-check] and also counts against the verdict. Pass --json for a machine-readable version of the same report.

Choosing what to install

You do not have to take every plugin. The most common starting point is memory alone:

$ ./bin/trailhead install --plugin lore
# or a couple of them
$ ./bin/trailhead install --plugin lore --plugin camp --plugin craft

The flags available on install:

FlagMeaning
--harness NAMETarget a harness explicitly instead of auto-detecting. Repeatable.
--plugin NAMEInstall only these plugins. Repeatable. Replaces the configured set entirely.
--no-campSkip installing or updating the camp CLI on PATH.
--no-loreSkip installing or updating the lore CLI on PATH.
--no-portageSkip installing or updating the portage CLI on PATH.
--config PATHDrive the install from a TOML config. Absolute, or relative to the repo's config/ directory. Defaults to config/default.toml.
--quietSuppress progress lines. The summary is still printed.
--jsonEmit a machine-readable summary.

Command-line flags are runtime overrides of the config file: --plugin replaces the resolved plugin set, and --harness overrides detection. Keep in mind that trailhead update re-wires from config/default.toml, so a plugin you left out of a narrower install comes back on the next update.

Config files, for finer control

To go further than the flags allow — picking individual subagents and skills, targeting several harnesses differently, or pointing a skill at your own file — write a config. Drop *.toml files in the repo's config/ directory; everything there except default.toml is gitignored, so your own configs never show up as changes in the checkout.

# config/minimal.toml
install_camp_cli = true
install_lore_cli = true
install_portage_cli = false

# Default plugin set, applied to every detected or named harness.
plugins = ["lore", "camp", "craft"]

[[harness]]
name = "claude_code"

    # Map form: pick specific subagents and skills.
    # Omit a key to mean "all of them".
    [[harness.plugins]]
    name = "craft"
    subagents = ["architect", "executor", "code-reviewer"]
    skills = ["plan", "execute", "review"]
$ ./bin/trailhead install --config minimal.toml

A plugin written as a bare string expands to all of its subagents and skills. Every skill and subagent you wire in costs context on every agent turn, so installing narrowly is a real optimization, not just tidiness.

If a config points a subagent or skill at a file outside the repository, the install summary names it explicitly. Content installed as trusted agent instructions is never wired in silently.

Where trailhead puts things

Trailhead follows the freedesktop base directory specification on every platform, macOS included — it deliberately does not use ~/Library/Application Support. The XDG_* environment variables override the defaults when set.

LocationContents
~/.local/state/trailhead/composed/The composed plugin trees per harness
~/.local/state/trailhead/bin/The CLI shim directory added to your PATH
~/.local/state/lore/vaults/default/Your default memory vault, a git repository
~/.local/state/lore/The derived search index
~/.config/lore/config.jsonThe vault registry
~/.local/state/trailhead/core-vault/trailhead’s own read-only core vault, copied from the checkout
~/.config/camp/groups/Your group definitions, one TOML file each
~/.config/outpost/config.tomlThe Outpost daemon’s config, including the checkout trailhead keeps up to date

On Windows these resolve under %APPDATA% and %LOCALAPPDATA% instead. Each application also honours its own override variable — LORE_CONFIG_DIR, CAMP_STATE_DIR, and so on — which is how the test suite avoids touching real data.

Upgrading

$ trailhead update --check   # read-only: is anything behind?
$ trailhead update           # fetch, fast-forward, and re-wire — asks first

update fast-forwards your checkout to its tracked branch and re-wires every plugin. It asks for confirmation first, or takes --yes. It refuses a checkout with uncommitted changes, and if re-wiring fails partway, it rolls the checkout back so a failed upgrade changes nothing. If your outpost config.toml names a checkout, the same command also fast-forwards, rebuilds, and restarts the outpost daemon. A successful run ends by printing doctor’s host-readiness verdict line.

--check fetches at most once every 24 hours; --window changes that interval and --timeout how long the fetch may take. With the trailhead plugin installed, a new agent session runs the same check and mentions it when you are behind. It never upgrades on its own. Set session_start_update_check = false in your config, or TRAILHEAD_DISABLE_UPDATE_CHECK in the environment, to turn the notice off.

Upgrades are additive. Re-running install only ever adds. Removing a plugin from your config does not remove it from the install. To actually drop pieces, uninstall and re-install with a narrower config.

Uninstalling

trailhead uninstall is all-or-nothing: it removes every plugin from every harness, all the CLI shims, and the PATH integration. It prompts for confirmation on a terminal; --yes skips the prompt.

$ trailhead uninstall

Your data survives. The lore vault, your camp groups, and each plugin's data directory are all left alone, so a later re-install picks up where you left off. Remove the shell profile line by hand afterwards if you are done for good.

Command reference

CommandWhat it does
trailhead installInstall plugins into your harness(es) and the plugin CLIs onto PATH
trailhead uninstallRemove the entire install. Keeps your data. --yes, --quiet, --json
trailhead doctorRead-only report of what is installed. --json
trailhead updateUpgrade the install, and a configured outpost daemon, from the checkout's tracked branch. --check, --automatic, --json, --yes, --dry-run, --timeout SECONDS, --window SECONDS
trailhead shellenvPrint the shell environment to evaluate. --shell fish|zsh|bash
trailhead outpost <verb>Manage the outpost daemon: start, stop, status, restart, open, enable, disable
trailhead gateway registerRegister this agent session with Outpost’s gateway. The plugin’s SessionStart hook runs the same step for you
trailhead core show <kind>/<name>Print a record from trailhead’s own read-only core vault

Running trailhead with no arguments prints a grouped menu. Errors are reported as a clean trailhead: <message> on stderr with a non-zero exit, never as a Python traceback.

Troubleshooting

The installer says it could not find a harness

It still builds the CLI shims, warns you, and exits non-zero. Re-run with --harness claude_code to install the plugins explicitly. If you are on Claude Code, check that ~/.claude exists.

lore or camp is not found after installing

The shellenv line is missing from your profile, or you have not restarted your shell. Run trailhead doctor and look at the shim directory line.

camp remove leaves me in a deleted directory

That is the shell wrapper being absent. camp remove still completes its work and prints the repo to return to, but cannot change your directory, and says so in a one-line tip. Add the shellenv line and restart your shell.

camp new creates the workspace but no session

camp could not reach tmux. The workspace is still created and its path printed, with a warning naming the reason. Install tmux, then run camp attach <slug> to open the session.

doctor ends with HOST NOT READY

Each item marked [missing] prints the command that fixes it and the step of the install guide it belongs to. Run each fix, then run trailhead doctor again; one fix can reveal the next.

The agent cannot see the new skills

Plugins are loaded when a session starts. Quit the agent session and start a fresh one.

doctor warns that something shadows trailhead

A pip-installed trailhead console script earlier on your PATH can shadow the shellenv shell function, or be shadowed by it. The editable install is only a development convenience — nothing depends on it. If the two disagree, remove the pip install and rely on the shell function.

Python is too old

trailhead doctor reports the python3 it sees. If it is below 3.11, install a newer Python and make sure it comes first on your PATH.
