Getting started

Installing Trailhead

Trailhead installs by cloning the repository and running one command. There is no package to download, no remote fetch, and no pip install step — the checkout is the source.

Requirements

  • Python 3.11 or newer. Trailhead has zero third-party runtime dependencies — the standard library is all it needs. Your system python3 may well be older than 3.11; check with python3 --version before you start.
  • git. Used for the checkout and for the memory vault, which is itself a git repository.
  • A supported shell — bash, zsh, or fish.
  • An agent harness. Claude Code is the harness that ships today. Trailhead detects it by the presence of a ~/.claude directory.
  • The GitHub CLI (gh), authenticated — only needed if you want portage or ranger to open, watch, and merge pull requests.

Install

Clone the repository somewhere permanent and run the installer. Where you put the checkout matters a little: it stays on disk and remains the source of everything trailhead installs, so pick a location you are not going to clear out.

$ git clone https://github.com/trailhead-ai/trailhead.git
$ cd trailhead
$ ./bin/trailhead install

With no flags, install auto-detects your harness, installs all six agent-plugins, and builds command-line shims for the plugins that ship a CLI. It prints a summary of what it did and what you still need to do.

Here is what happens under the covers, in order:

  1. Detect harnesses on the machine.
  2. Resolve the effective config — the config file (default config/default.toml) merged with any command-line overrides, producing the set of harnesses, plugins, and individual subagents and skills to install.
  3. Compose and wire each harness under a lock: build the selected plugin trees, then register them with the harness.
  4. Build the CLI shim directory — one small wrapper per CLI-bearing plugin, each pointing back at your checkout.
  5. Bootstrap lore — create the default vault as a git repository, seed its config, and install the vault write guardrail. This step is idempotent, and if it fails the whole install fails rather than leaving you half-configured.
  6. Print the summary.
Trailhead does not edit your shell profile. It is brew-style: the installer tells you the line to add, and you add it. The next section is not optional — without it, none of the plugin CLIs will resolve.

Put the CLIs on your PATH

Add this line to your shell profile, using the absolute path to the checkout you just cloned:

eval "$(/absolute/path/to/trailhead/bin/trailhead shellenv)"

Then restart your shell, or re-evaluate the line in the current one. shellenv detects your shell from $SHELL; pass --shell fish, --shell zsh, or --shell bash to override it. For fish, the profile is usually ~/.config/fish/config.fish; for zsh, ~/.zshrc; for bash, ~/.bashrc.

What that one line sets up:

  • TRAILHEAD_ROOT, pointing at your checkout.
  • The shim directory on your PATH, so lore, camp, portage, and ranger resolve.
  • A trailhead shell function that re-resolves itself from the profile line at every shell startup. This is why moving or re-cloning the checkout only requires editing that one line — you do not need to re-run the installer.
  • A camp wrapper function. Camp never moves your shell by itself, so this wrapper is what lets camp new and camp remove actually change your working directory. Without it those commands still do their work and print the path, they just leave you where you were — and camp resume refuses outright rather than printing a line that would do nothing.

Finally, start a fresh agent session so the harness picks up the newly installed plugins. An already-running session will not see them.

Verify

trailhead doctor prints a read-only report of what is installed. It never changes anything and never gates — it always exits 0 unless the report itself crashes, so treat it as information, not as a pass/fail check.

$ trailhead doctor
trailhead doctor (read-only report):

  claude_code:
    marketplace: trailhead (registered)
    installed: camp, craft, lore, outpost, portage, ranger

  CLIs on PATH:
    lore: /Users/you/.local/state/trailhead/bin/lore
    camp: /Users/you/.local/state/trailhead/bin/camp
    portage: /Users/you/.local/state/trailhead/bin/portage
    ranger: /Users/you/.local/state/trailhead/bin/ranger
    trailhead: /Users/you/.local/state/trailhead/bin/trailhead
  shim dir: /Users/you/.local/state/trailhead/bin (present)
  python3: Python 3.11.9

Pass --json for a machine-readable version of the same report.

Choosing what to install

You do not have to take all six plugins. The most common starting point is memory alone:

$ ./bin/trailhead install --plugin lore
# or a couple of them
$ ./bin/trailhead install --plugin lore --plugin camp --plugin craft

The flags available on install:

FlagMeaning
--harness NAMETarget a harness explicitly instead of auto-detecting. Repeatable.
--plugin NAMEInstall only these plugins. Repeatable. Replaces the configured set entirely.
--no-campSkip installing or updating the camp CLI on PATH.
--no-loreSkip installing or updating the lore CLI on PATH.
--no-portageSkip installing or updating the portage CLI on PATH.
--config PATHDrive the install from a TOML config. Absolute, or relative to the repo's config/ directory. Defaults to config/default.toml.
--quietSuppress progress lines. The summary is still printed.
--jsonEmit a machine-readable summary.

Command-line flags are runtime overrides of the config file: --plugin replaces the resolved plugin set, and --harness overrides detection.

Config files, for finer control

To go further than the flags allow — picking individual subagents and skills, targeting several harnesses differently, or pointing a skill at your own file — write a config. Drop *.toml files in the repo's config/ directory; everything there except default.toml is gitignored, so your own configs never show up as changes in the checkout.

# config/minimal.toml
install_camp_cli = true
install_lore_cli = true
install_portage_cli = false
install_ranger_cli = false

# Default plugin set, applied to every detected or named harness.
plugins = ["lore", "camp", "craft"]

[[harness]]
name = "claude_code"

    # Map form: pick specific subagents and skills.
    # Omit a key to mean "all of them".
    [[harness.plugins]]
    name = "craft"
    subagents = ["architect", "executor", "code-reviewer"]
    skills = ["plan", "execute", "review"]
$ ./bin/trailhead install --config minimal.toml

A plugin written as a bare string expands to all of its subagents and skills. Every skill and subagent you wire in costs context on every agent turn, so installing narrowly is a real optimization, not just tidiness.

If a config points a subagent or skill at a file outside the repository, the install summary names it explicitly. Content installed as trusted agent instructions is never wired in silently.

Where trailhead puts things

Trailhead follows the freedesktop base directory specification on every platform, macOS included — it deliberately does not use ~/Library/Application Support. The XDG_* environment variables override the defaults when set.

LocationContents
~/.local/state/trailhead/composed/The composed plugin trees per harness
~/.local/state/trailhead/bin/The CLI shim directory added to your PATH
~/.local/state/lore/vaults/default/Your default memory vault, a git repository
~/.local/state/lore/The derived search index
~/.config/lore/config.jsonThe vault registry
~/.config/camp/groups/Your group definitions, one TOML file each

On Windows these resolve under %APPDATA% and %LOCALAPPDATA% instead. Each application also honours its own override variable — LORE_CONFIG_DIR, CAMP_STATE_DIR, and so on — which is how the test suite avoids touching real data.

Upgrading

$ cd /path/to/trailhead
$ git pull
$ ./bin/trailhead install

There is no trailhead update command; pulling and re-running the installer is the upgrade path.

Upgrades are additive. Re-running install only ever adds. Removing a plugin from your config does not remove it from the install. To actually drop pieces, uninstall and re-install with a narrower config.

Uninstalling

trailhead uninstall is all-or-nothing: it removes every plugin from every harness, all the CLI shims, and the PATH integration. It prompts for confirmation on a terminal; --yes skips the prompt.

$ trailhead uninstall

Your data survives. The lore vault, your camp groups, and each plugin's data directory are all left alone, so a later re-install picks up where you left off. Remove the shell profile line by hand afterwards if you are done for good.

Command reference

CommandWhat it does
trailhead installInstall plugins into your harness(es) and the plugin CLIs onto PATH
trailhead uninstallRemove the entire install. Keeps your data. --yes, --quiet, --json
trailhead doctorRead-only report of what is installed. --json
trailhead shellenvPrint the shell environment to evaluate. --shell fish|zsh|bash
trailhead outpost <verb>Manage the outpost daemon: start, stop, status, restart

Running trailhead with no arguments prints a grouped menu. Errors are reported as a clean trailhead: <message> on stderr with a non-zero exit, never as a Python traceback.

Troubleshooting

The installer says it could not find a harness

It still builds the CLI shims, warns you, and exits non-zero. Re-run with --harness claude_code to install the plugins explicitly. If you are on Claude Code, check that ~/.claude exists.

lore or camp is not found after installing

The shellenv line is missing from your profile, or you have not restarted your shell. Run trailhead doctor and look at the shim directory line.

camp resume refuses to run, or camp new does not move me into the workspace

Both are the shell wrapper being absent. camp new and camp remove still complete their work and print the workspace path, but cannot change your directory; camp resume stops rather than printing an instruction that would silently do nothing. Add the shellenv line and restart your shell.

The agent cannot see the new skills

Plugins are loaded when a session starts. Quit the agent session and start a fresh one.

doctor warns that something shadows trailhead

A pip-installed trailhead console script earlier on your PATH can shadow the shellenv shell function, or be shadowed by it. The editable install is only a development convenience — nothing depends on it. If the two disagree, remove the pip install and rely on the shell function.

Python is too old

trailhead doctor reports the python3 it sees. If it is below 3.11, install a newer Python and make sure it comes first on your PATH.
