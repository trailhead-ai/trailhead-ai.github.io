Plugin

craft — process

craft is the engineering process your agent actually follows: rituals for shaping an idea into a settled spec, delivering it one vertical slice at a time — each planned, built test-first, and reviewed — and condensing what you learned into decision records. Each stage is run by a specialist subagent in its own context.

An agent given a task and no process will produce something. It will look plausible, it will compile, and it will be reviewed by nobody — least of all by the model that just wrote it, which has every token of its own reasoning in context and no distance from it. The failure mode is not bad code. It is code that quietly answers a slightly different question than the one you asked, built on an assumption nobody checked, with the reasoning that justified it buried in a conversation that is about to be compacted away.

Three things go wrong, and they compound. Intent drifts: the change that lands is not the change that was described, and the gap only shows up later, in production or in a code review that has to reconstruct the intent from the diff. Context blows out: one long session accumulates raw test output, full diffs, log dumps, and exploratory dead ends until the model doing the expensive thinking is spending most of its budget re-reading noise. And nothing is ever adversarially checked: the same context that produced a design also evaluates it, so the assumptions that were wrong at the start are still wrong at the end, having never met a reader whose job was to break them.

craft is the counter-structure. It is a set of skills your agent invokes by name and a roster of subagents those skills dispatch, with the discipline written down where the agent will read it: interrogate before you plan, freeze before you build, prove an unknown before you build on it, write the test before the implementation, and let someone who was not there review the result.

craft has no command-line tool. Unlike lore, camp, and portage, there is nothing to run from a shell. craft is skills and subagents only — it exists inside your harness and nowhere else. The scripts that ship with it are internal helpers the skills and agents run themselves — gates that check a ritual’s output before it is written, gatherers that assemble what a ritual reads, and resolvers like the maturity check below — plus the leak-gate pair, which installs as a git hook.

The core idea: split the work, not the context

Every craft ritual is an orchestration. The session you are talking to decides what needs doing and dispatches a subagent to do it; the subagent works in an isolated context, and only its conclusion comes back. The raw material — ten thousand lines of test output, a full base..HEAD diff, a log file, the contents of six source files it read to answer one question — never enters the main conversation at all.

That buys two things at once. The first is economics: the expensive model never pays to read raw logs. A test run comes back as pass or fail from a cheap model; a log becomes the four relevant lines; a documentation lookup becomes one path:line pointer. The second matters more. Because each subagent starts fresh, it is a genuinely independent reader. The reviewer that checks a slice has never seen the argument that produced it. The agent attacking a spec’s premises has no investment in the spec. Adversarial review is not a prompt asking a model to be critical of itself — it is a different context, given the artifact and not the reasoning behind it.

The tiering follows from this. Cheap, fast models run the mechanical helpers. Mid-tier models write code against a clear contract. The most capable models are reserved for the roles where fresh eyes actually change the answer: review, troubleshooting, architecture, research.

The ritual arc

The main path runs from a fuzzy idea to landed, reviewed, recorded work:

brainstorm → gauntlet → (slice → plan → execute → review)* → tidy-followups → distill

The bracketed loop runs once per slice, delivering a settled spec one vertical increment at a time, and /craft:drive runs one turn of it end to end. Each stage hands a specific artifact to the next, and the handoffs are the point — a stage can only start when the previous one has produced something concrete enough to attack.

brainstorm — fuzzy idea to draft spec

You say you have been thinking about something. /craft:brainstorm first resolves the declared maturity of every repository the work touches (see Project Maturity below), then interrogates: what problem, why now, what does done look like, what is explicitly out of scope, what happens when it fails and how would you know. It does not write anything until the understanding is shared and confirmed. A brainstorm exits with exactly one spec: when discovery turns up more than one spec’s worth of work, it specs the smallest piece that still delivers value and captures the rest as deferred tasks. The output is a spec at status draft — problem, objectives, maturity, acceptance criteria, required interfaces, non-goals, constraints, UI direction, open questions. Brainstorm cannot advance it; that edge belongs to the gauntlet.

gauntlet — adversarial passes before the spec settles

/craft:gauntlet runs eight passes in parallel against a draft spec, each in an isolated context: fact verification (the falsifiable claims, checked), premise attack, the four council lenses, an internal-consistency audit, and a plan-divergence probe. The main session adjudicates rather than delegating the synthesis, and hands back one compact recommendation — a synthesis, a recommended outcome, and a proposed disposition for each Critical — which you accept or override in a single round-trip. Only then is the spec stamped with its review provenance and flipped to ready. All eight passes are required — if a pass agent is not installed, the gauntlet names it and stops rather than presenting a partial review as a complete one.

slice — choose the next increment

/craft:slice reads the ready spec fresh, derives the slices still left to build, and chooses the smallest next one that clears the value floor. A slice is a vertical increment: when it is done, the system is observably more valuable to the spec’s own consumer. The skill states that value claim to you, then writes the chosen slice as an in-progress parent task linked to the spec. Slices are chosen one at a time, against current information, and the choice is made again after each one ships — which is why the spec stays ready for the whole loop rather than being decomposed up front.

plan — one slice to a task graph

/craft:plan runs against that slice parent. It explores the codebase, proposes approaches, designs end to end, names the known unknowns, and decomposes the slice into tasks. Each task can be built, tested, and committed on its own, and each carries its test contract — the behaviors that must fail as tests before any implementation exists. A task that defers its tests is not a valid task. The plan then goes through a mandatory council review before it is presented for your approval.

execute — task by task, gated

/craft:execute is a controller loop, not a builder. It walks the task graph in topological order, dispatching only runnable leaves. For each task: if it rests on an unresolved unknown, an assumption-prover writes a throwaway test that proves or disproves it before anything is built on top. Then an executor writes the failing tests, implements, mutation-checks every test-contract item, and commits. Then, scaled to the size of the change, a drift-gate checks conformance behind the task — did the diff deliver what the plan said, does the executor’s status claim hold against the actual change, is the next task unblocked. Quality and style are explicitly out of scope for that gate; they are deferred to whole-change review, not dropped.

Once every task is terminal, a sequential pipeline runs on the whole change: a test-runner gate, a simplifier pass that removes cross-task duplication and dead scaffolding the incremental build left behind, a whole-change correctness review, a conditional security audit, the flow-out ritual that writes what was learned back to memory, and the close. The security phase is fail-closed — any ambiguity about whether it should run means it runs.

review — the whole change

/craft:review dispatches code-reviewer against the full base..HEAD diff and its intent document, in a fresh context with no memory of how the change was built. It returns findings categorized Critical / Important / Minor — not fixes, and not style opinions. It runs standalone before a merge, and again as execute’s correctness phase.

drive — one turn of the loop

/craft:drive takes a ready spec through one slice end to end: it runs the slice, plan, and execute procedures inline, hands the branch to portage, closes the slice, and stops at the slice boundary to report. Choosing reports one of three outcomes — a chosen slice, a spec with nothing left to build, or an early stop. The driver resolves nothing it does not own: a slice that spans more than one repository is escalated rather than assigned to a guess.

tidy-followups — what is worth doing now

Building a spec leaves follow-ups behind. Once the slice loop has ended, /craft:tidy-followups gathers every follow-up recorded against the spec and presents a reasoned shortlist — the ones worth doing now, each with a one-line reason waiting would make it costlier — and lists the rest by title. It writes nothing until you confirm the chosen set. Then it refines each chosen follow-up and nests the ones that qualify under one new buildable parent, ending with the commands to build it and to distill.

distill — finished work to ADRs

/craft:distill is the backward pass and the last stage. It reads completed spec and task work, clusters related specs into logical design changes rather than drafting one record per spec, and drafts one ADR per design change — only for decisions a future implementer would get wrong without knowing. Nothing is written until a human has dispositioned every draft. On approval it creates the ADRs, supersedes the decision records they absorbed so each points at the ADR that replaced it, re-synthesizes the area profiles the work touched, and flips the member specs complete. It is the only path that marks a spec complete.

refine and polish — the two side entrances

Not all work arrives through a spec. /craft:refine takes a standalone task — one with no parent and no children — and promotes it from open to ready by drafting its Delivers / Test contract / Files payload from the code and the vault, citing every derived answer, and escalating only an irreducible operator decision. It is self-serve by default: it fills gaps itself before it involves a human. /craft:execute runs the same procedure inline when handed a standalone open task, from the same shared document, so the two callers cannot drift apart.

/craft:polish handles the other end: a batch of post-implementation fix-ups. It collects the list, resolves any ambiguity with you in one consolidated turn, writes a brief, and dispatches executor to do the mechanical work in a cheaper context — keeping iteration off the main session’s expensive tokens.

Vocabulary

The rituals share a small set of terms. They are worth reading once, because the skills use them precisely.

Spec

The what and why of a change, and the artifact everything downstream is checked against. A spec walks draft → ready → complete. It stays draft through brainstorming, the gauntlet moves it to ready, it holds ready for the whole slice loop because another slice can always be added, and distill marks it complete. Once ready it is settled, and lore refuses an ordinary edit to its body. A correction that stays inside what the spec already decides is an in-place amend, made through /lore:correct. If planning or implementation surfaces something that would change its objectives, acceptance criteria, or non-goals, you do not edit it — you re-enter brainstorming and produce a new spec that links back. Task-level uncertainty (which library, how to name a module) is resolved inline in planning instead; the bounce-back rule is for shifts in what and why, not how.

ADR

An architecture decision record: context, decision, consequences, alternatives rejected, kept to roughly one screenful on the theory that a decision that does not fit a screen is usually two decisions. An ADR walks draft → active, and from active to superseded or dropped. Once active its body is frozen — an in-scope correction is an amend, and changing your mind creates a new, superseding ADR rather than an edit. The supersession is recorded as an edge, so a reader landing on the old record finds the new one.

Slice, plan, and task

A slice is a vertical increment of a spec: when it is done, the spec’s consumer is observably better off. Its quality bar is valuable, small, and testable. Slices are chosen one at a time by /craft:slice, and each is written as a parent task record linked to its spec.

A plan is not a document. It is that parent plus one child task per component-shaped unit of work beneath the slice, wired with containment edges and ordered with dependency edges. A task can be built, tested, and committed independently, and it carries a test contract. The graph is not frozen at plan time — a task that turns out too large is split, new work is appended, and the graph stays the single source of truth for what is left. The parent is never dispatched as a unit of work.

Standalone task vs plan task

A standalone task has no parent and no children: it is the whole unit of work. A plan task is a child of a parent plan. The distinction is determined mechanically from the record graph, never by reading the prose, because the two have opposite handling — a standalone task is refined and then executed as its own unit, while a plan task found on its own means the run was rooted in the wrong place and should be re-rooted at its parent.

Delivers / Test contract / Files

The payload that makes a task executable. Delivers is what is complete and testable when the task is done. Test contract is the behaviors the failing tests must verify before any implementation code exists. Files is what gets created or modified. A task without this payload is not ready; producing it is exactly what refine does, and every derived answer in it must cite the code it came from.

The gauntlet

The adversarial review a draft spec survives before it settles: eight parallel passes, run on every spec with no skip flag. The main session adjudicates — never a subagent — and proposes a disposition for every Critical, which you accept or override in one round-trip. A Critical left at revise holds the spec at draft and sends its finding back for another round: the spec has not yet survived, which is the review working rather than the spec failing.

The council

The four-lens panel — builder, breaker, attacker, advocate — dispatched as four parallel calls in isolated contexts. Members do not see each other’s responses, each rates severity against a written Critical bar for its own lens, and the synthesis is always done by the main session. Membership is single-sourced, so the planning skill’s council step, the gauntlet’s lens pass, and /craft:consult all convene the same panel.

ADRs are written backward

craft authors ADRs in one direction only. Distill reads work that already landed and condenses the decisions it embodies, so an ADR records what the code actually settled rather than what was intended before anyone built it. Neither brainstorm nor the gauntlet produces an ADR. A decision worth noting before the work starts is a lightweight lore decision record, captured as you go — and distill later supersedes it with the ADR that absorbs it.

Project Maturity

A repository declares its standard of care in a ## Project Maturity section of its agent-instruction file (CLAUDE.md, for example), naming one of prototype, early, or production:

## Project Maturity

early

The level calibrates how hard the rituals push on five concerns: backwards compatibility, migration and backfill, rollback and reversibility, production failure visibility, and cross-consumer blast radius. A gap in any of them is a Minor finding for a prototype, Important for an early project, and Critical in production. Brainstorm resolves the level for every repository the work touches before it starts asking questions, records it in the spec, and the council’s reviewers read it from there. A repository that declares nothing is treated as production, and so is a section that is ambiguous — one naming more than one level, or a file with two such sections — so keep any comparison to another level out of the section body.

Status tokens

Subagents in the execute loop return a fixed vocabulary rather than prose, so the controller can branch on it:

TokenMeaning and handling
DONEThe task is built and committed. Proceed to the conformance gate.
DONE_WITH_CONCERNSBuilt, but with caveats. Correctness or scope concerns are addressed before review; observations are noted and the loop continues.
NEEDS_CONTEXTThe prompt was insufficient. Supply what was missing and re-dispatch at the same tier — this is not a model-capability problem.
BLOCKEDThe work could not proceed. Diagnose the cause — missing context, insufficient reasoning capacity, a task that is too large, or a wrong plan — before re-dispatching. Re-running the same prompt hoping for a different result is explicitly called out as a red flag.

The assumption-prover returns VALIDATED or INVALIDATED alongside the same two escape tokens. An invalidated assumption stops the build — the design may need to change, and building on top of it is the specific failure the prover exists to prevent.

Where craft keeps its records

Specs, plans, tasks, and ADRs are lore records, and craft never writes them as files itself. Every ritual creates and updates them through the lore CLI, following one shared reference the skills read at runtime: the spec, plan, and task bodies are rendered from craft’s own templates and piped to lore record create, a plan’s graph is built from --parent and --depends-on edges, and status moves through lore record update, validated against each kind’s vocabulary.

That is why craft — alone among the plugins — has a dependency: it needs lore for storage. If the lore CLI is absent entirely, the planner falls back to a documented manual-write path.

craft is never a dependency of the other plugins — nothing in lore, camp, portage, or outpost requires it, and you can run any of them without it. The dependency runs the other way: craft needs lore to store what it produces.

The pre-commit leak gate

craft ships a small, generic guard for a specific problem: working in a private repo and a public one at the same time, and accidentally committing a private string — an internal service name, a customer identifier, an unreleased product codename — into the repo that ships publicly.

The gate is denylist-driven and ships zero private strings itself. Every forbidden token lives in a machine-local denylist file that is never tracked in any repository, one regex per line, matched case-insensitively. scripts/install-hooks.sh installs the gate as a pre-commit hook; the installer is idempotent and chain-safe, so an existing pre-commit hook is preserved and runs first, and because .git/hooks/ is never committed, the absolute paths baked into the generated hook stay on your machine.

It is fail-closed. A missing, unreadable, or pattern-empty denylist makes the gate exit 2 — an error, not a pass. It exits 0 only when it actually certified the tree clean, 1 when it found a leak (printing relpath:lineno:token for each hit), and never 0 when it could not check. A gate that silently passes when its configuration is missing is worse than no gate, because you would trust it.

Scope and honest limits

There is no CLI, and no vanilla usage. craft only exists inside an agent harness. If you want to use the process without an agent, there is nothing here for you — the skills are instructions written for a model, and the subagents are dispatched by one.

Claude Code is the only harness implemented. The subagent dispatch and skill-invocation model craft depends on is wired through Trailhead’s harness seam, but Claude Code is what ships today.

lore is a hard dependency. Specs, plans, tasks, and ADRs are lore records, and craft has no other place to keep them.

The rituals are not cheap. Eight parallel gauntlet passes, a four-lens council review, per-task conformance gates, and a whole-change pipeline all cost tokens and wall-clock time. Every skill carries an explicit skip gate for exactly this reason: a change with two tasks, no unknowns, and a hundred lines of scope should just be built, and the skills say so.

Several review disciplines are enforced by prompt, not by machinery. The gauntlet halts on a missing pass agent and the simplifier’s write scope is checked mechanically, but the bulk of craft’s discipline is instructions an agent chooses to follow. It works because the instructions are specific and the checks are staged — not because anything stops a model that decides to skip a step.
