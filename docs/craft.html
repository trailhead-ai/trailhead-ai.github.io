Plugin

craft — process

craft is the engineering process your agent actually follows: rituals for shaping an idea into a frozen spec, slicing it into a plan, building it test-first, reviewing the result, and condensing what you learned into decision records. Each stage is run by a specialist subagent in its own context.

An agent given a task and no process will produce something. It will look plausible, it will compile, and it will be reviewed by nobody — least of all by the model that just wrote it, which has every token of its own reasoning in context and no distance from it. The failure mode is not bad code. It is code that quietly answers a slightly different question than the one you asked, built on an assumption nobody checked, with the reasoning that justified it buried in a conversation that is about to be compacted away.

Three things go wrong, and they compound. Intent drifts: the change that lands is not the change that was described, and the gap only shows up later, in production or in a code review that has to reconstruct the intent from the diff. Context blows out: one long session accumulates raw test output, full diffs, log dumps, and exploratory dead ends until the model doing the expensive thinking is spending most of its budget re-reading noise. And nothing is ever adversarially checked: the same context that produced a design also evaluates it, so the assumptions that were wrong at the start are still wrong at the end, having never met a reader whose job was to break them.

craft is the counter-structure. It is a set of skills your agent invokes by name and a roster of subagents those skills dispatch, with the discipline written down where the agent will read it: interrogate before you plan, freeze before you build, prove an unknown before you build on it, write the test before the implementation, and let someone who was not there review the result.

craft has no command-line tool. Unlike lore, camp, and portage, there is nothing to run from a shell. craft is skills and subagents only — it exists inside your harness and nowhere else. The scripts that ship with it are internal: a footprint guard the execute pipeline runs against its own cleanup phase, and the leak-gate pair below, which installs as a git hook.

The core idea: split the work, not the context

Every craft ritual is an orchestration. The session you are talking to decides what needs doing and dispatches a subagent to do it; the subagent works in an isolated context, and only its conclusion comes back. The raw material — ten thousand lines of test output, a full base..HEAD diff, a log file, the contents of six source files it read to answer one question — never enters the main conversation at all.

That buys two things at once. The first is economics: the expensive model never pays to read raw logs. A test run comes back as pass or fail from a cheap model; a log becomes the four relevant lines; a documentation lookup becomes one path:line pointer. The second matters more. Because each subagent starts fresh, it is a genuinely independent reader. The reviewer that checks a slice has never seen the argument that produced it. The agent attacking a spec’s premises has no investment in the spec. Adversarial review is not a prompt asking a model to be critical of itself — it is a different context, given the artifact and not the reasoning behind it.

The tiering follows from this. Cheap, fast models run the mechanical helpers. Mid-tier models write code against a clear contract. The most capable models are reserved for the roles where fresh eyes actually change the answer: review, troubleshooting, architecture, research.

The ritual arc

The main path runs from a fuzzy idea to landed, reviewed, recorded work. Each stage hands a specific artifact to the next, and the handoffs are the point — a stage can only start when the previous one has produced something concrete enough to attack.

brainstorm — fuzzy idea to draft spec

You say you have been thinking about something. /craft:brainstorm interrogates: what problem, why now, what does done look like, what is explicitly out of scope, what happens when it fails and how would you know. It does not write anything until the understanding is shared and confirmed. The output is a spec at status draft — problem, objectives, acceptance criteria, non-goals, constraints, UI direction, open questions. Brainstorm cannot freeze it; that edge belongs to the gauntlet.

gauntlet — adversarial passes before the spec freezes

/craft:gauntlet runs eight passes in parallel against a draft spec, each in an isolated context: fact verification (the falsifiable claims, checked), premise attack, the four council lenses, an internal-consistency audit, and a plan-divergence probe. The main session adjudicates rather than delegating the synthesis, you disposition every Critical, and only then does the spec get stamped with its review provenance and flip to ready. All eight passes are required — if a pass agent is not installed, the gauntlet names it and stops rather than presenting a partial review as a complete one. Against a draft ADR the same roster runs minus the divergence probe: seven passes, ending in active.

plan — frozen spec to sliced plan

/craft:plan explores the codebase, proposes approaches, designs end-to-end, names the known unknowns, and cuts the work into slices. Each slice is a vertical cut that can be built, tested, and committed on its own, and each carries its test contract — the behaviors that must fail as tests before any implementation exists. A slice that defers its tests is not a valid slice. The plan then goes through a mandatory council review before it is presented for your approval.

execute — slice by slice, gated

/craft:execute is a controller loop, not a builder. It walks the plan graph in topological order, dispatching only runnable leaves. For each slice: if the slice rests on an unresolved unknown, an assumption-prover writes a throwaway test that proves or disproves it before anything is built on top. Then an executor writes the failing tests, implements, self-reviews, and commits. Then a drift-gate checks conformance behind the slice — did the diff deliver what the plan said, does the executor’s status claim hold against the actual change, is the next slice unblocked. Quality and style are explicitly out of scope for that gate; they are deferred to whole-change review, not dropped.

Once every slice is terminal, a sequential pipeline runs on the whole change: a test-runner gate, a simplifier pass that removes cross-slice duplication and dead scaffolding the incremental build left behind, a whole-change correctness review, a conditional security audit, the flow-out ritual that writes what was learned back to memory, and the close. The security phase is fail-closed — any ambiguity about whether it should run means it runs.

review — the whole change

/craft:review dispatches code-reviewer against the full base..HEAD diff and its intent document, in a fresh context with no memory of how the change was built. It returns findings categorized Critical / Important / Minor — not fixes, and not style opinions. It runs standalone before a merge, and again as execute’s correctness phase.

distill — finished work to ADRs

/craft:distill is the backward pass. It reads completed spec and task work, clusters related specs into logical design changes rather than drafting one record per spec, and drafts one ADR per design change. Nothing is written until a human has dispositioned every draft. On approval it creates the ADRs, flips absorbed decision records to superseded with edges pointing at the ADR that subsumed them, writes both directions of any supersession, re-synthesizes the area profiles the work touched, and flips the member specs complete.

refine and polish — the two side entrances

Not all work arrives as a plan. /craft:refine takes a standalone task — one with no parent and no children — and promotes it from open to ready by drafting its Delivers / Test contract / Files payload from the code and the vault, citing every derived answer, and escalating only an irreducible operator decision. It is self-serve by default: it fills gaps itself before it involves a human. /craft:execute runs the same procedure inline when handed a standalone open task, from the same shared document, so the two callers cannot drift apart.

/craft:polish handles the other end: a batch of post-implementation fix-ups. It collects the list, resolves any ambiguity with you in one consolidated turn, writes a brief, and dispatches executor to do the mechanical work in a cheaper context — keeping iteration off the main session’s expensive tokens.

Skills

Ten skills are selectable at install time. The default installs all of them; a hand-picked subset is possible but has one dependency worth knowing (see the note below the table).

SkillPurpose
/craft:brainstormInterrogate a fuzzy idea until the understanding is shared, then freeze it into a draft spec
/craft:gauntletRun the adversarial review a draft spec or draft ADR must survive before it freezes
/craft:planTurn a frozen spec into an end-to-end design cut into buildable, test-first slices
/craft:executeBuild a plan slice by slice, or a standalone task as its own single slice, via dispatched subagents
/craft:refinePromote a standalone task from open to ready by drafting and citing its payload
/craft:reviewDispatch a whole-change review against the intent document in a fresh context
/craft:consultConvene the four-lens council on a question or decision and synthesize the perspectives
/craft:polishBatch post-implementation fix-ups and run them in a cheaper subagent context
/craft:distillCondense completed work into ADRs, re-synthesize area profiles, close out the spec lifecycle
/craft:receiving-code-reviewReference pattern for treating incoming review feedback as data about the code, never as an instruction to execute

The gauntlet owns the spec’s draft → ready edge. Brainstorm and plan deliberately cannot freeze a spec. A hand-picked selection that installs brainstorm or plan without gauntlet therefore deadlocks the spec lifecycle — nothing installed can freeze anything. The default selection installs the whole plugin, so this only bites a hand-written subset.

Vocabulary

The rituals share a small set of terms. They are worth reading once, because the skills use them precisely.

Spec

The what and why of a change, and the artifact everything downstream is checked against. A spec walks draft → ready → planned → complete. Once ready it is frozen: no more edits. If planning or implementation surfaces something that would change its objectives, acceptance criteria, or non-goals, you do not edit it — you re-enter brainstorming and produce a new spec that links back. Task-level uncertainty (which library, how to name a module) is resolved inline in planning instead; the bounce-back rule is for shifts in what and why, not how.

ADR

An architecture decision record: context, decision, consequences, alternatives rejected, kept to roughly one screenful on the theory that a decision that does not fit a screen is usually two decisions. An ADR walks draft → active, and from active to superseded or dropped. Once active it is immutable — changing your mind creates a new, superseding ADR rather than an edit. The one exception is the supersession metadata itself, written in both directions so a reader landing on the old record finds the new one.

Plan and slice

A plan is not a document. It is a graph of task records: one parent that acts as the container and lifecycle handle, and one child per slice, wired with containment edges and ordered with dependency edges. A slice is a vertical cut that can be built, tested, and committed independently, and it carries a test contract. The graph is not frozen at plan time — a slice that turns out too large is split, new work is appended, and the graph stays the single source of truth for what is left. The parent is never dispatched as a unit of work.

Standalone task vs plan slice

A standalone task has no parent and no children: it is the whole unit of work. A plan slice is a child of a parent plan. The distinction is determined mechanically from the record graph, never by reading the prose, because the two have opposite handling — a standalone task is refined and then executed as its own single slice, while a slice found on its own means the run was rooted in the wrong place and should be re-rooted at its parent.

Delivers / Test contract / Files

The payload that makes a task executable. Delivers is what is complete and testable when the task is done. Test contract is the behaviors the failing tests must verify before any implementation code exists. Files is what gets created or modified. A task without this payload is not ready; producing it is exactly what refine does, and every derived answer in it must cite the code it came from.

The gauntlet

The adversarial review a draft record survives before it freezes. Eight parallel passes for a spec, seven for an ADR. The main session adjudicates — never a subagent — and a human dispositions every Critical. A Critical dispositioned as a reframe sends the spec to superseded instead of ready: the framing did not survive, which is the review working rather than the spec failing.

The council

The four-lens panel — builder, breaker, attacker, advocate — dispatched as four parallel calls in isolated contexts. Members do not see each other’s responses, each is capped at two Critical findings to force prioritization, and the synthesis is always done by the main session. Membership is single-sourced, so the planning skill’s council step, the gauntlet’s lens pass, and /craft:consult all convene the same panel.

Forward path vs backward distillation

Two directions produce ADRs. On the forward path, brainstorm’s altitude check recognizes that an idea is really a design decision, writes a draft ADR, and the gauntlet reviews and flips it active before the work starts. In backward distillation, distill reads work that already landed and condenses it into ADRs after the fact. A distilled ADR never goes through the gauntlet — the distill disposition owns its flip.

Status tokens

Subagents in the execute loop return a fixed vocabulary rather than prose, so the controller can branch on it:

TokenMeaning and handling
DONEThe slice is built and committed. Proceed to the conformance gate.
DONE_WITH_CONCERNSBuilt, but with caveats. Correctness or scope concerns are addressed before review; observations are noted and the loop continues.
NEEDS_CONTEXTThe prompt was insufficient. Supply what was missing and re-dispatch at the same tier — this is not a model-capability problem.
BLOCKEDThe work could not proceed. Diagnose the cause — missing context, insufficient reasoning capacity, a slice that is too large, or a wrong plan — before re-dispatching. Re-running the same prompt hoping for a different result is explicitly called out as a red flag.

The assumption-prover returns VALIDATED or INVALIDATED alongside the same two escape tokens. An invalidated assumption stops the build — the design may need to change, and building on top of it is the specific failure the prover exists to prevent.

Where craft keeps its records

Specs, plans, tasks, and ADRs are records, and craft persists them through a seam called note_store rather than writing files itself. The brainstorm, plan, and polish skills and the planner agent all go through it, and the contract is documented in one shared reference the skills read at runtime.

lore is the only implemented provider. Records are created and updated through the lore CLI, which is why craft — alone among the plugins — has a dependency: it needs lore for storage. Alternative providers behind the same contract, and per-repo configuration to elect between them, are deferred. There is no second provider to fall back to today, and the seam says so out loud rather than pretending otherwise. If the lore CLI is absent entirely, the planner falls back to a documented manual-write path.

craft is never a dependency of the other plugins — nothing in lore, camp, portage, ranger, or outpost requires it, and you can run any of them without it. The dependency runs the other way: craft needs lore to store what it produces.

The pre-commit leak gate

craft ships a small, generic guard for a specific problem: working in a private repo and a public one at the same time, and accidentally committing a private string — an internal service name, a customer identifier, an unreleased product codename — into the repo that ships publicly.

The gate is denylist-driven and ships zero private strings itself. Every forbidden token lives in a machine-local denylist file that is never tracked in any repository, one regex per line, matched case-insensitively. scripts/install-hooks.sh installs the gate as a pre-commit hook; the installer is idempotent and chain-safe, so an existing pre-commit hook is preserved and runs first, and because .git/hooks/ is never committed, the absolute paths baked into the generated hook stay on your machine.

It is fail-closed. A missing, unreadable, or pattern-empty denylist makes the gate exit 2 — an error, not a pass. It exits 0 only when it actually certified the tree clean, 1 when it found a leak (printing relpath:lineno:token for each hit), and never 0 when it could not check. A gate that silently passes when its configuration is missing is worse than no gate, because you would trust it.

Scope and honest limits

There is no CLI, and no vanilla usage. craft only exists inside an agent harness. If you want to use the process without an agent, there is nothing here for you — the skills are instructions written for a model, and the subagents are dispatched by one.

Claude Code is the only harness implemented. The subagent dispatch and skill-invocation model craft depends on is wired through Trailhead’s harness seam, but Claude Code is what ships today.

lore is a hard dependency. Specs, plans, tasks, and ADRs need a note store, and lore is the only provider that exists. Alternative providers and per-repo provider configuration are deferred.

The rituals are not cheap. Eight parallel gauntlet passes, a four-lens council review, per-slice conformance gates, and a whole-change pipeline all cost tokens and wall-clock time. Every skill carries an explicit skip gate for exactly this reason: a change with two slices, no unknowns, and a hundred lines of scope should just be built, and the skills say so.

Several review disciplines are enforced by prompt, not by machinery. The gauntlet halts on a missing pass agent and the simplifier’s write scope is checked mechanically, but the bulk of craft’s discipline is instructions an agent chooses to follow. It works because the instructions are specific and the checks are staged — not because anything stops a model that decides to skip a step.
