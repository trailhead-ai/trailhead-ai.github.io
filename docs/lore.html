Plugin

lore — memory

A git-backed vault of markdown records your agent writes to as it works and searches before it decides. Nine record kinds, a query language, and a session log that turns loose findings into durable notes.

Every agent session starts amnesiac. The model has your code and whatever you paste into the window, and nothing else — not the reason the retry budget is 3 and not 5, not the migration approach that was tried in March and abandoned, not the fact that the flaky integration test is flaky because of a clock skew nobody has fixed. That context was expensive to acquire and it evaporates when the window closes. The next session rediscovers it, or more often gets it wrong.

lore is where that context goes instead. During a session the agent logs findings as cheap session candidates; at the end it applies judgment and promotes the keepers into durable records — decisions, lessons, tasks, area profiles. Records are markdown files with a JSON sidecar, living in a git repository under your state directory. Everything is plain text you can read, grep, diff, and revert without any of the tooling present.

The whole surface is a command-line tool. There is no MCP server and no service to sign up for: the agent runs lore over Bash and git over Bash, and that is the entire integration. A SQLite full-text index sits alongside the vault to make search fast, but it is a derived cache — delete it and lore reindex rebuilds it from the markdown, which is always the source of truth.

Key concepts

The vault

A vault is a git repository of markdown records. lore init scaffolds the default one at $XDG_STATE_HOME/lore/vaults/default (~/.local/state/lore/vaults/default on a stock machine, macOS included) and registers it in ~/.config/lore/config.json. Each record is two files under a per-kind directory: <kind>/<name>.md for the body and <kind>/<name>.json for the sidecar — title, status, keywords, related-record edges, timestamps, and provenance.

Because a vault is an ordinary git repo, backup and sharing are just a remote. lore sync stages, commits, pulls, and pushes every configured vault; lore status names any vault holding records that exist in exactly one place.

Layered vaults

You can register more than one vault and lore searches them together. Each carries a scope, and a write routes to the most specific vault that matches: repo > product > suite > team > default. Your personal default vault is the unconditional floor — a write that matches nothing else lands there. A vault can be restricted to particular record kinds with --record, and lore vault resolve --kind <kind> reports where a write would land right now before you make it.

A vault registered with --shared is marked untrusted. Its hits still show up in search, but the human output wraps them in an <external-memory> fence with the content entity-escaped, and the skills instruct the agent to treat fenced content as reference data — never as instructions. This is the seam that lets a team share a vault without letting a teammate’s note steer someone else’s agent.

Records: a closed set of nine kinds

The kind set is closed on purpose. Nine kinds is a taxonomy an agent can hold in its head and apply consistently; an open set becomes a junk drawer.

KindWhat it records
decisionA non-obvious architectural choice and the reasoning behind it — the lightweight, in-flight form
adrA formal architecture decision record; convention treats one as immutable once it is active
lessonA mistake plus a concrete prevention check, so the same mistake is catchable next time
taskAnything worth seeing through: implementation work, a deferred item, an abandoned approach, an external thing to watch. Carries parent and depends-on edges
areaThe mental model of a codebase area — files, gotchas, conventions. Feeds the area map
specA frozen specification artifact, the input a plan is built from
collaborationWorking-style preferences and conventions — how you want to be worked with
blobFreeform capture that genuinely fits nothing else
sessionOne note per working session: the running candidate log

Status vocabulary

Every kind has its own canonical status set, and a write outside the vocabulary is rejected. The first value is the default applied when --status is omitted on create.

KindStatuses (first is the create default)
taskopen → ready → in-progress → done; off-path blocked, dropped, superseded
specdraft → ready → planned → complete; off-path superseded, dropped
adrdraft → active → superseded / dropped
decisionactive → superseded / dropped
lessonactive, conditional
sessiondirty → clean
area, blob, collaborationactive

Areas and the area map

An area record is a profile of one part of your system: a name, a one-line summary, a keyword set, and a body describing the files, gotchas, and conventions. lore areas prints the area map — every area’s name, summary, and keywords in one compact listing. That is what makes recall explainable rather than lucky: the agent reads the map as part of normal task analysis, matches the task to one or more areas, and pulls that area’s accumulated memory with lore search 'area:<name>'. It can then say “I searched the auth-service area because this touches the login flow” instead of producing context from nowhere.

Queries

Search speaks a subset of KQL against the index. Facets and scalars combine with boolean operators:

  • Scalar fields: kind:, status:, repo:, team:, product:, suite:
  • List facets: area:, keyword:, phase:, and related-<kind>: for every record kind (related-task:, related-spec:, …)
  • Labels: label.<key>:<value> for an exact match, has:label.<key> for existence. A namespaced key uses dot-for-slash — the stored key claude-code/model is queried as label.claude-code.model:opus
  • Ranges: >=, <=, >, < on created-at, updated-at, last-referenced-at
  • Composition: and / or / not, a - exclusion prefix, parenthesized groups, kind:(spec or task) shorthand, quoted phrases, and bare terms for BM25-ranked full text over title, keywords, and body

An unknown field is a hard error with a “did you mean” suggestion rather than a silent empty result. Wildcards, fuzzy matching, boosts, and regex are deliberately unsupported.

Sessions, candidates, and the flush watermark

A session record is one note per working session, keyed by the harness session id (or the worktree name as a fallback). During work the agent appends candidates — lore session candidate --kind decision --phase build, body piped in on stdin. A candidate is deliberately cheap: it costs a line, it needs no title, and it commits to nothing. Capture liberally; judgment comes later. Logging a candidate flips the session dirty.

Flush is where judgment happens. The agent reads the session with lore session show --json, finds the outstanding candidates — those logged after the flushed-at watermark stored in the sidecar annotations — and evaluates each one: promote it to a durable record, or discard it as session-local noise. Then lore flush stamps the session clean, writes a new watermark, and commits. The watermark is what makes flush re-runnable mid-session without re-promoting everything you already dealt with.

lore flush commits the session record’s own paths and nothing else. The records the flush just created usually live in a different, scope-routed vault — so lore sync afterwards is not optional. Flush ends by naming any vault still holding unsynced work.

The derived index

Search reads a SQLite database with an FTS5 table at $XDG_STATE_HOME/lore/index.sqlite, covering every configured vault at once. It is strictly derived: the markdown and sidecar files are the source of truth, the index is a projection, and on any disagreement the text wins. lore reindex rebuilds it from the vault tree. Nothing you care about is lost if the file is deleted.

How an agent uses it day to day

The loop is three moves, and only the first two are automatic-feeling:

  • Search before deciding. Starting work in an unfamiliar area, or about to repeat an approach that may have failed before — run lore areas, then lore search 'area:<name>'. This is a decision the agent makes, not something that happens to it.
  • Capture during work. A decision made in passing, a dead-end, a gotcha, something deferred — each becomes a session candidate as it arises. This is the default capture path; a direct lore record create is reserved for deliberately authored artifacts (a task, spec, or area profile) or an explicit “pin this one now”.
  • Flush at the end. Evaluate the outstanding candidates into records, flip the session clean, sync the vaults.

Marking that an existing record was used is a separate, cheaper move: lore session referenced <kind>/<name> stamps last-referenced-at so you can later find the notes that actually earn their keep.

CLI reference

Every command is self-describing; lore <subcommand> --help is authoritative.

CommandWhat it does
lore initBootstrap the machine: scaffold the default vault, seed config.json, install the write guardrail and the agent ruleset. Idempotent
lore statusReport ruleset drift per harness and every vault holding uncommitted, unpushed, or remote-less records
lore search <query>Query the global index. --json, --limit N (default 20)
lore areasPrint the area map — every area’s name, one-liner, and keywords
lore recordcreate / update / show / rename / delete. Sidecar metadata via --status, --keyword, --related KIND=NAME, --label, --annotation; routing via --repo / --product / --suite / --team / --vault
lore sessioncandidate (log a finding, body on stdin), referenced (stamp a record as used), show (read the session, --json for the sidecar and watermark)
lore flushFlip a session clean and commit it. No argument for the current session, all for every dirty session, or a KQL query to select a set
lore syncStage, commit, pull, push. --vault <name> for one, --message to set the commit subject
lore tasklist --vault <name> (filter by --status, or --runnable for ready tasks whose dependencies are done) and graph <name> for the containment subtree plus depends-on edges
lore vaultadd / delete / ls / config, plus resolve --kind <kind> to see where a write would route
lore reindexRebuild the derived index from the vault tree

A worked example

Capture during a debugging session, recall it weeks later:

# Starting work — what do we already know about this area?
$ lore areas
$ lore search 'area:auth-service and kind:(decision or lesson)'

# Mid-session: a finding worth keeping. Cheap, no title, no ceremony.
$ printf '%s' "Refresh-token rotation breaks the mobile client because it
retries the same token on a 401. Server-side grace window is the fix, not
client changes." | lore session candidate --kind lesson --phase build

# An existing record actually got used — stamp it.
$ lore session referenced decision/rotate-refresh-tokens-on-use

# End of session: promote the keepers, then commit everything.
$ lore session show --json          # candidates + flushed-at watermark
$ lore record create --kind lesson \
    --title "Refresh rotation needs a server-side grace window" \
    --keyword auth --keyword mobile \
    --related area=auth-service \
    --related decision=rotate-refresh-tokens-on-use
$ lore flush                        # session -> clean, watermark stamped
$ lore sync                         # commit + push every vault

# Three weeks later, a different session, no shared context:
$ lore search 'area:auth-service and kind:lesson'
$ lore record show lesson/refresh-rotation-needs-a-server-side-grace-window

Vault writes go through the CLI

lore init installs a PreToolUse guardrail into your harness settings that blocks Edit, Write, MultiEdit, and NotebookEdit against any path inside a vault. The hook canonicalizes paths at call time, so it follows the default symlink to wherever it currently points; generated permissions.deny rules sit underneath it as defense in depth. One subtree is exempt: each vault’s sites/ directory, a free-write zone for static pages that ride the vault’s sync.

The point is not distrust of the agent. It is that a record is a body and a sidecar and an index row, written under a lock; a hand-edit produces a record that looks fine on disk and is invisible to search. Routing every write through lore record keeps those three in agreement.

Scope and honest limits

Recall is pull-only. The agent searches the vault when it decides to. There is no hook that injects relevant memory into a conversation automatically — the UserPromptSubmit classifier that would do that is designed and deferred, not built. In practice this means memory works when the agent has a reason to look, and a note nobody searches for is a note nobody reads.

The guardrail does not cover Bash. A shell redirect, sed -i, or cp into a vault is opaque at PreToolUse time. That gap is covered only by the prohibition in the agent ruleset — a rule the model follows, not a mechanism that stops it.

Claude Code is the only harness implemented. The ruleset install goes through Trailhead’s harness seam and degrades visibly for a harness without user-level ruleset support, but nothing else is shipped today.

Search is lexical, not semantic. Facets plus BM25 full text. There is no embedding index; asking a question in words the notes do not use will miss. An opt-in local semantic index is on the roadmap and deliberately not a dependency.

Shared-vault content is untrusted input. The human output fences and escapes it, but --json output carries no fence — it exposes a shared flag per hit instead, and the body arrives verbatim.

Relations are not checked for existence. --related task=nope validates clean; the index materializes whatever edges happen to resolve. Renames are swept (lore record rename rewrites inbound references), but a typo is yours to find.

One install caveat worth stating plainly: the lore CLI itself works in a vanilla checkout — its path resolvers fall back to plain XDG_CONFIG_HOME / XDG_STATE_HOME (or their POSIX defaults under $HOME) when Trailhead is not importable. But lore init reaches for Trailhead’s harness detection to install the ruleset and the guardrail, so the full bootstrap expects the Trailhead checkout to be present. You also need a git identity — $LORE_EMAIL or git config --global user.email — before the first record write, and lore init warns you if neither resolves.
